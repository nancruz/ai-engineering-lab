COURSE MATERIAL

Connect a real tool-calling model

Use this in Module 1, week 2. Until then the lab's scripted models are enough. Pick one route and record exactly what you used: the model tag or ID, the provider or server version, and the date.

Local route — Ollama

  1. Install Ollama from its official instructions and start the local server. Keep it on localhost.
  2. Pull a model that supports tool calling and that your machine can run. Ollama's own tool-calling examples use the qwen3 family; pick a size that fits your memory and check the exact tag on Ollama's model library page before pulling it.
ollama pull <tag>        # for example a small qwen3 size
ollama list              # record the tag and digest

Run the supplied adapter on one task and save everything:

python3 tracks/agents/lab/run.py --task credential-policy --model ollama:<tag> \
  --out projects/ops-agent/artifacts/runs/week-02/supplied-credential.json

The adapter in real_model.py sends your messages and the tool definitions to /api/chat with stream: false. It reads message.tool_calls and sends each result back as a message with role: "tool" and tool_name. It saves the raw response and token counts under model_log. It handles one tool call per turn and records any extra calls it ignored; your own loop in week 2 handles all of them.

Cloud route — Amazon Bedrock

If you completed RAG Module 7, reuse that AWS account, region and least-privilege role. The Converse API supports client-side tool use: you pass toolConfig.tools[].toolSpec (name, description and inputSchema.json); when the response's stopReason is tool_use, the assistant message contains toolUse blocks with a toolUseId, name and input. You run the tool and send a user message containing one toolResult block per call, with the matching toolUseId, the content (for example [{"json": …}]) and status set to success or error. Check the current Bedrock documentation for which models support tool use in your region.

Write this as app/models/bedrock.py following the adapter interface in the project contract. Set a budget alert before your first run; agent runs make many calls.

What a failure means

SymptomNext action
Connection refusedStart the server and check the port. Do not change the loop.
Model answers in prose, never calls a toolCheck that the model supports tools and that you sent the definitions. Small models often skip tools; record it as a result, then try a larger size.
invalid_arguments on most callsRead the details. This is Module 2's material: improve descriptions and enums, then measure again.
Same call repeated until the budget endsThe repeat rule and stop rules from week 3 handle this. Save the trajectory as a test case.
Correct-looking answer, wrong end stateTrust the checks over the text. Open side_effects and drafts.
Slow first responseSeparate model loading from warm inference and record your hardware.

The lab's world is fictional and runs locally; nothing your agent does in it reaches a real system. Keep it that way until Module 7's pilot, and even then start in approval-only mode.
