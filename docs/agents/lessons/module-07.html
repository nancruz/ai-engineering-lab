Module 07 — Operate agents in production

Weeks 25–28 · 3 hours per week · one evolving ops-agent project.

Start here

The last four weeks turn the agent into something a team could rely on: every call traced, cost and latency managed with evidence, failures that end safely, and a supervised pilot with a kill switch and a rollback path.

Working result: A deployed, authenticated agent service in approval-only mode, with traces, a cost and reliability dashboard, tested recovery from faults, a kill switch and a pilot hand-off document.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/, infra/ or artifacts/ mean files inside projects/ops-agent/.

Week 25 — Trace every model and tool call

Make every run explainable from its trace alone.

Session A — Start and inspect (60 minutes)

Read the OpenTelemetry semantic conventions for generative AI agent spans (see references): a root span per agent invocation, a span per model call with model and token attributes, and a span per tool execution with the tool name. They are still marked as in development, so pin the version you follow. Decide what content you will record: prompts and tool arguments can contain sensitive data, so make capture opt-in and redact it.

Session B — Build or change (60 minutes)

Write app/tracing.py with the OpenTelemetry SDK (pin it). Emit spans for the run, each model call and each tool call, with tokens, stop reason, gate decision, taint and run ID as attributes. Export to a local file or console first; optionally run a local trace viewer in a container. Put the trace ID in every trajectory line so the two records link up.

Session C — Run and verify (60 minutes)

Trace a full rollback-check including the approval pause and resume, linked by run ID. From the trace alone, find the slowest span and the most expensive model call. Add a test that a credential-like string in tool arguments is redacted before export.

Save: Tracing module, one linked trace across a pause, and the redaction test.

Move on when: you can explain a run's cost and latency without opening its trajectory file. If the hour ends first, keep your current work and resume the unfinished step next session.

The service returned HTTP 200 and the trace shows no errors, but the answer was wrong. What does that tell you?

  1. The model provider had an outage.
  2. Traces show what happened, not whether it was right. You need quality signals as well: online checks and sampled grading of real runs.
  3. The trace sampler dropped the error.

Agents fail semantically while every call succeeds. Run your end-state checks online where you can, and grade a sample of production runs with the same graders as Module 5.

Week 26 — Cut cost and latency with evidence

Change one lever at a time and keep only what the suite supports.

Session A — Start and inspect (60 minutes)

In the cost workbench, try routing a share of tasks to a smaller model with and without escalation, and try compaction and caching. Then compute your own baseline from week 25 traces: cost per successful task and p50/p95 latency per task family.

Session B — Build or change (60 minutes)

Implement two levers behind configuration switches. Candidates: prompt caching (stable content first, if your provider supports it), tighter tool-output caps, routing easy families to a smaller model with escalation when end-state checks fail, and running independent read-only tool calls in parallel.

Session C — Run and verify (60 minutes)

For each lever, run the eval suite with three trials and record cost per success, pass^3 per family and p95 latency. Keep a lever only if it improves cost or latency and the release gate still passes.

Save: Lever implementations, per-lever measurements and the configuration you keep.

Move on when: each kept change has a before/after measurement on the same suite. If the hour ends first, keep your current work and resume the unfinished step next session.

Routing to a smaller model halves cost per task, but success drops from 0.9 to 0.6 with no escalation. Cost per success still falls (0.5/0.6 ≈ 0.83 against 1/0.9 ≈ 1.11). What else must you check?

  1. Nothing: cost per success is the right single metric.
  2. That four in ten tasks now fail for users. Can failures be detected and escalated, and what does a failure cost the team?
  3. Whether the smaller model is newer.

Cost per success ignores the cost of failures. With escalation on detected failures, routing can save money without users seeing more failures. Try both in the workbench.

Week 27 — Recover from failures without side effects

Make every failure end in a known state.

Session A — Start and inspect (60 minutes)

List the failure modes and the behaviour you want for each: model API rate limits, errors and timeouts; a tool outage; malformed model output; budget exhaustion; a crash mid-run; and a bad prompt release.

Session B — Build or change (60 minutes)

Implement: retries with jittered backoff for model calls; a fallback model, recorded in the trace; a circuit breaker that makes a failing tool return a clear “unavailable” error; a kill switch in configuration that makes the gate refuse every side effect immediately; and per-run time limits that end in a partial result.

Session C — Run and verify (60 minutes)

Write fault-injection tests with a fake provider and fake tools. For each fault, assert that the run ends with a known stop reason, no side effect is duplicated and the user receives a partial result that says what is missing. Flip the kill switch in the middle of a run and assert that pending side effects are refused.

Save: Recovery mechanisms and the fault-injection test suite.

Move on when: every listed fault has a test, and none can produce a duplicate or unapproved side effect. If the hour ends first, keep your current work and resume the unfinished step next session.

The model provider is unavailable for ten minutes during an incident. What should the agent do?

  1. Retry until the provider recovers.
  2. Try the fallback; if that fails too, return what it has gathered, hand over to a person and keep its state so the run can resume.
  3. Answer from cached earlier responses.

During an incident, a fast and honest partial result is worth more than a silent retry loop. Saved state means no work is lost when the provider returns.

Week 28 — Ship a supervised pilot

Put the agent in front of real use, with tight limits and a way back.

Session A — Start and inspect (60 minutes)

Write the pilot plan: who uses it, which task families are on, and that the agent may only read and draft, with every side effect requiring approval. Add success criteria, stop criteria and an on-call runbook. Choose the deployment: a local service, or the AWS environment from RAG Module 7 if you built it (container, authentication, secrets).

Session B — Build or change (60 minutes)

Deploy behind authentication. Write a release manifest (model IDs, prompt versions, tool versions, gate policy, configuration hash) to artifacts/releases/<release-id>/manifest.json. Build a small dashboard from traces: tasks per day, online check pass rate, cost per success, approvals requested and granted, gate blocks and taint holds.

Session C — Run and verify (60 minutes)

Run twenty tasks through the deployed service. Practise three drills: flip the kill switch; roll back to the previous release manifest; resume a paused run after a redeploy. Write artifacts/pilot/handoff.md with results, residual risks and what you would allow the agent to do next, given evidence.

Save: Deployment, release manifest, dashboard, drill results and the hand-off document.

Move on when: another engineer could operate the pilot from your runbook and hand-off alone. If the hour ends first, keep your current work and resume the unfinished step next session.

In the pilot, what should the agent be allowed to do without a person?

  1. Anything the policy documents allow.
  2. Read and draft. Every side effect waits for an approval bound to its exact fields.
  3. Create low-severity tickets only.

Start with the least autonomy that still saves time, then widen it one task family at a time when the evidence supports it. Each widening is a release that goes through the gate.

Complete the final practical checkpoint. Your repository now contains a portfolio piece: an agent with tools, MCP, guardrails, evaluation and operations, plus the decision records that explain it.

Reference — concepts used in the experiments

Agent telemetry. The OpenTelemetry generative AI conventions define an agent invocation span, model-call spans (model, provider, input and output tokens, finish reason) and tool-execution spans (tool name, call ID). Message content and tool arguments are not captured by default because they often contain personal or secret data. Following the conventions lets any compatible backend read your traces.

Cost and latency levers. Input tokens dominate most agent bills, so the main levers are shorter tool outputs, compaction, caching a stable prefix, fewer turns (better tools, better stop rules) and routing work to smaller models where checks show they succeed. For latency: parallel independent calls, streaming the final answer and avoiding needless turns.

Reliability patterns. Retries with backoff and jitter only for retryable errors; idempotency keys for anything with an effect; circuit breakers so a failing dependency fails fast; fallbacks recorded in traces; a kill switch outside the model's reach; time limits that end in an honest partial result.

Rolling out autonomy. Common stages are shadow mode (the agent runs, people act), approval-only (the agent drafts, people approve), then autonomous for specific low-risk families with monitoring and a rollback path. Each step is justified by evaluation results and pilot data, not by a demo.

Worked example

Take the routing question from week 26. Suppose the large model costs 1 unit per task with 0.9 success, and the small model 0.5 units with 0.6 success. Routing everything small costs about 0.83 per success instead of 1.11, but 40% of tasks fail. With escalation (the large model retries detected failures), cost per task becomes 0.5 + 0.4 × 1 = 0.9 and success becomes 0.6 + 0.4 × 0.9 = 0.96, so cost per success is about 0.94. That is cheaper than large-only, with fewer failures, if your end-state checks can detect the failures. The cost workbench computes this from token counts.
