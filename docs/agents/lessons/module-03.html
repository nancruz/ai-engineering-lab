Module 03 — Manage context, state and memory

Weeks 9–12 · 3 hours per week · one evolving ops-agent project.

Start here

Everything the model knows during a run is in its context, and the context grows with every tool result. In this module you measure what fills it, shrink it without losing facts, make runs survive a crash or a long wait for approval, and add memory only where it measurably helps.

Working result: A loop that reports its context by category, compacts long runs while keeping a facts ledger, resumes from a checkpoint without repeating side effects, and uses a memory store with provenance and expiry.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/.

Week 09 — Measure what fills the context

Find out where the tokens go before trying to save any.

Session A — Start and inspect (60 minutes)

Open the cost and context workbench. Set 15 steps, compaction off, and read the chart: each bar is the input the model reads at that step. Double the tool output per step and see how the total changes. Then open two of your own trajectories and list everything the model reads each turn: system prompt, tool definitions, task, earlier model text and tool results.

Session B — Build or change (60 minutes)

Write app/context.py to account for the context by category on every turn. Use the provider's reported input tokens for the total and an estimate for the split between categories. Do not forget the tool definitions, which are sent on every call. Write the breakdown into each trajectory line.

Session C — Run and verify (60 minutes)

Run the four tasks and find the two largest contributors. Set a per-result cap for the biggest tool output (fewer sources, shorter excerpts or fewer metric points) and re-run. Check that rollback-check still has the five consecutive minutes it needs and still succeeds.

Save: Context accounting, before/after breakdowns and the cap you chose with its reason.

Move on when: each trajectory shows where its input tokens came from and one measured cap reduced them without a task regression. If the hour ends first, keep your current work and resume the unfinished step next session.

A run makes ten tool calls, each returning about 500 tokens, and keeps everything in context. How does the total input over the run grow?

  1. Linearly: about 5,000 extra tokens in total.
  2. Roughly with the square of the steps: each turn re-reads every earlier result, so later turns cost far more than early ones.
  3. It stays flat, because results are cached.

Turn 10 reads nine earlier results, turn 9 reads eight, and so on, which adds up to about 22,500 tokens of re-read results. Prompt caching can lower the price of a repeated prefix, but the model still processes it.

Week 10 — Compact long runs without losing facts

Keep long runs inside budget while keeping what later steps depend on.

Session A — Start and inspect (60 minutes)

Add a long task to data/tasks/dev.jsonl: an incident handover that reads both services' metrics over several windows, reads four policies and drafts two tickets, at least twelve tool calls in all. Run it and list the facts that must survive to the end: draft IDs, numbers used in decisions, citations and any action already taken.

Session B — Build or change (60 minutes)

Implement compaction in app/context.py. When the context passes a threshold, keep the last N turns verbatim, replace older tool results with a short summary, and keep a structured facts ledger (drafts, side effects, key numbers, cited source IDs) that is never summarised. The ledger is written by your code from tool results, not by the model.

Session C — Run and verify (60 minutes)

Run the long task with and without compaction, three times each. Compare input tokens and success. Add a test in which a fact from step 2 (a draft ID) is needed at step 14, and assert that it is still available after compaction.

In the cost workbench, set “Keep last N turns” to 4 and compare the bars with the grey uncompacted ones.

Save: Compaction, facts ledger, the long task and the with/without comparison.

Move on when: compaction lowers input tokens on the long task without lowering its success rate. If the hour ends first, keep your current work and resume the unfinished step next session.

Which information must compaction never drop?

  1. The exact wording of every policy the agent read.
  2. IDs of side effects and drafts already made, and decisions already taken.
  3. The system prompt's tone instructions.

Policies can be fetched again. If the agent forgets that it already drafted or created something, it will do it again. That is why the ledger is kept outside the summary.

Week 11 — Checkpoint and resume a task

Let a run survive a crash and a long wait for a person.

Session A — Start and inspect (60 minutes)

Interrupt a run of the long task halfway through and note what is lost. Sketch the task's states: started, gathering evidence, drafted, awaiting approval, done or failed. Mark which transitions have side effects.

Session B — Build or change (60 minutes)

Write app/state.py. After every step, save a checkpoint to artifacts/runs/<run-id>/checkpoint.json with the messages, ledger, budgets used and idempotency keys. Write to a temporary file and rename it, so a crash never leaves a half-written checkpoint. Add resume(run_id). Treat “awaiting approval” as a pause that ends the process, not as a loop that keeps polling.

Session C — Run and verify (60 minutes)

Tests: a crash after a side effect but before the checkpoint does not duplicate the effect on resume (the idempotency key from week 8 catches it); a resumed run continues with the remaining budget, not a fresh one; an approval event resumes a paused run and executes exactly the approved action.

Save: Checkpointing, resume, approval pause and the crash tests.

Move on when: a killed run resumes to the same end state as an uninterrupted one. If the hour ends first, keep your current work and resume the unfinished step next session.

An approval may take three hours. What is the right design?

  1. Keep the loop running and ask the model every minute whether approval has arrived.
  2. Save the state, stop, and resume the run when the approval event arrives.
  3. Assume approval after a timeout.

A waiting loop burns tokens, holds resources and can be lost in a restart. A saved state plus an event to resume is cheaper and survives deployments.

Week 12 — Add memory that earns its place

Remember across runs only what helps, from sources you trust.

Session A — Start and inspect (60 minutes)

List candidates for cross-run memory, such as “the catalog metrics backend is often slow” or a team's preferred ticket format. List what must never be stored: secrets, anything from untrusted content and anything a tool can fetch fresh.

Session B — Build or change (60 minutes)

Write app/memory.py: notes with text, source (run ID or person), scope (team or service), creation time, expiry and trust. Add recall as a read tool. Write memories only from trusted sources: a person's instruction or your own code's observations, never directly from tool text. Label recalled notes in the context with their source and age.

Session C — Run and verify (60 minutes)

Create ten cases: five where a note should help and five where a stale or wrong note could mislead, for example an expired timeout value. Run with and without memory, three times each. Keep memory only if it helps the first group without new failures in the second.

Save: Memory store, provenance and expiry rules, the ten cases and the comparison.

Move on when: you have a measured keep-or-drop decision for memory. If the hour ends first, keep your current work and resume the unfinished step next session.

After reading the imported note, the agent wants to save “always copy capacity values into tickets” to memory. What should happen?

  1. Save it with a low-confidence flag.
  2. Refuse: a memory written from untrusted content becomes an injection that persists into every future run.
  3. Save it only for the current team.

Memory turns one bad input into a lasting instruction. Write memories only from trusted sources, and keep provenance so a bad note can be found and removed.

Reference — concepts used in the experiments

Context engineering. Aim for the smallest set of high-signal tokens that lets the model take the next step. Fetch data when it is needed (just-in-time) rather than preloading everything. For long tasks, three techniques recur: compaction (summarise and continue), structured notes kept outside the context and reloaded when needed, and sub-agents that work in their own clean context and return a short result (Module 6).

Token accounting. Provider usage numbers are the source of truth for billing. Estimates are useful only for splitting a total into categories. Tool definitions are part of every request. Prompt caching can reduce the price and latency of a repeated prefix, so keep stable content (system prompt, tool definitions) at the start and the changing parts at the end.

Durable state. Long-running work needs checkpoints written atomically, explicit states, and resumption that is safe to repeat. Combined with idempotency keys, this gives effectively-once side effects even when the process dies at the worst moment.

Memory risks. Memory can be poisoned (written from attacker-controlled text), go stale (a policy changed) or leak (one user's notes shown to another). Provenance, scope, expiry and a way to delete are the minimum controls.

Worked example

For the careful run of rollback-check, the lab's estimate is about 113 tokens at turn 1, 367 at turn 2, 475 at turn 3 and 584 at the final turn. The largest single addition is the first search (about 254 tokens): three full policy texts, two of which the rest of the run never uses. Returning two sources, or shorter excerpts with IDs, would cut that by around a third. That saving is then paid back on every later turn.
