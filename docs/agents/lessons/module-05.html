Module 05 — Evaluate agents on outcomes and reliability

Weeks 17–20 · 3 hours per week · one evolving ops-agent project.

Start here

Agents are judged by what they leave behind (tickets, rollbacks, answers) and by whether they do it every time, not once. In this module you build a task suite with end-state checks, add trajectory graders, measure reliability across repeated trials and gate releases on the results.

Working result: A versioned task suite with development and final splits, graders for outcomes and trajectories, a multi-trial runner reporting pass@k and pass^k, and a release gate that blocks a seeded regression.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/.

Week 17 — Build a task suite with end-state checks

Define success by what happened, then make it repeatable.

Session A — Start and inspect (60 minutes)

Read check() in agent.py: it inspects side effects, drafts and the final answer, not the wording of the trajectory. Draft about twenty tasks across families: policy questions, rollback met / not met / metrics failing, missing evidence, injection, approvals and the long handover. For each, write the environment fixture and the end-state checks.

Session B — Build or change (60 minutes)

Store tasks in data/tasks/dev.jsonl and data/tasks/final.jsonl, split by family so paraphrases of one task never cross the split. Write the runner behind make -C projects/ops-agent eval: each task runs in a fresh environment (new tracker, approvals, memory), and the runner saves every trajectory plus a summary.

Session C — Run and verify (60 minutes)

Prove the checks work: for each family, run one known-good and one known-bad scripted trajectory and confirm the checks pass and fail as expected. Add a test that refuses to run the final split without an explicit --final flag.

Save: Task suite with split manifest, runner and the check-validation tests.

Move on when: every family has a check that is shown to catch a failure. If the hour ends first, keep your current work and resume the unfinished step next session.

Why check the end state rather than read the transcript?

  1. Transcripts are too long to store.
  2. The transcript can say “I drafted the approval request” when no draft exists, or hide a side effect behind a confident summary.
  3. End-state checks are always faster.

The world is the ground truth. Check the tracker, the drafts and the rollbacks directly, then use the transcript to explain why.

Week 18 — Grade trajectories, not just answers

Catch runs that end well but behave badly on the way.

Session A — Start and inspect (60 minutes)

Open the trial grader workbench. Switch graders on and off and watch the pass rates change. Select rollback-check trial 3: the end state is correct, but the agent tried a rollback that the gate blocked. Decide whether that should count as a pass.

Session B — Build or change (60 minutes)

Add code-based trajectory graders: forbidden tool attempted, required evidence read before a claim (metrics before “the condition is met”), step limit, valid citation IDs and no blocked repeats. Use a model-graded rubric only for qualities code cannot check, such as whether a handover summary is clear. Calibrate it against twenty labels you write yourself and record where it agrees and disagrees.

Session C — Run and verify (60 minutes)

Run the dev suite, open every disagreement between graders and decide which graders block a release and which are reported only. Write the decision into configs/release-policy.json.

Save: Trajectory graders, the calibrated rubric with its agreement counts, and the blocking/reporting decision.

Move on when: every grader is either blocking or report-only, for a written reason. If the hour ends first, keep your current work and resume the unfinished step next session.

A trial reached the correct end state, but the agent attempted a rollback the gate blocked. How should you treat it?

  1. Pass: the outcome was right.
  2. Fail the whole suite.
  3. Count the outcome as correct, and track the attempt as a separate safety signal that you watch and can gate on.

The gate did its job, but the attempt shows how the model behaves when the gate is missing or wrong. Keep outcome and safety metrics separate so neither hides the other.

Week 19 — Measure reliability across repeated trials

Separate “can do it” from “does it every time”.

Session A — Start and inspect (60 minutes)

In the workbench, move k from 1 to 6 and watch pass@k and pass^k separate. Read the definitions in the reference section and check one value by hand.

Session B — Build or change (60 minutes)

Add --trials n to your runner, with an independent environment per trial. Report per task: pass rate, pass@k and pass^k (using the estimators in grading.py), cost per success and the spread of steps and tokens.

Session C — Run and verify (60 minutes)

Run five trials of the dev suite. Mark tasks as flaky when their pass rate is between 0.2 and 0.8. Read the trajectories of one flaky task, change one thing (a tool description, a stop rule or the prompt) and re-measure with the same number of trials.

Save: Multi-trial runner, reliability report and one flaky-task investigation with before/after numbers.

Move on when: your report shows pass^k per task and you have re-measured one fix. If the hour ends first, keep your current work and resume the unfinished step next session.

The on-call team will run this agent several times every day. Which number matters most to them?

  1. pass@k: whether at least one of k tries works.
  2. pass^k: whether all k tries work.
  3. The best single run you have recorded.

pass@k suits settings where you can retry and keep any success, such as generating candidates. Someone relying on the agent every day experiences every run, so consistency is what they feel.

Week 20 — Gate agent releases on evaluation

Turn measurements into a decision your pipeline can enforce.

Session A — Start and inspect (60 minutes)

Before running anything final, finish configs/release-policy.json. Hard gates: zero forbidden side effects executed, all security tests pass, no approval bypass. Soft targets: pass^3 per family not below the last release minus a stated tolerance, cost per success within budget, and a minimum number of trials.

Session B — Build or change (60 minutes)

Implement make -C projects/ops-agent gate, which reads eval artifacts and exits non-zero on any hard failure while reporting soft regressions. Run the unit and security tests with scripted models on every change. Run the bounded real-model evaluation on demand before a release.

Session C — Run and verify (60 minutes)

Seed two regressions, one at a time: remove the taint hold, then change the prompt so citations disappear. Confirm the gate blocks each one and names the reason, then restore. Run the final split once for this milestone and record that it has been used.

Save: Release policy, gate command, the two blocked releases and the final-split result.

Move on when: the gate fails for a relevant defect, not only for a crash. If the hour ends first, keep your current work and resume the unfinished step next session.

A new prompt raises mean pass@1 from 0.70 to 0.74, on twenty tasks with one trial each. Should you ship it?

  1. Yes, it is an improvement.
  2. Not on this evidence: run more trials, compare pass^k per family and check that the safety metrics did not move.
  3. No, because any prompt change is risky.

With one trial per task, a difference of 0.04 is within run-to-run noise. Repeat the trials, compare families, and let the hard gates decide on safety.

Reference — concepts used in the experiments

What to grade. Outcome graders check the end state of the environment. Trajectory graders check how the agent got there: tools used, forbidden attempts, steps. Answer graders check the final text: required facts, citations, abstention. Use code wherever the property can be checked mechanically, a model-graded rubric where it cannot (calibrated against human labels), and people for the cases where the two disagree.

Capability and regression suites. A capability suite contains tasks the agent cannot yet do reliably; it shows progress. A regression suite contains tasks it already does; it should stay near 100% and blocks releases. Move tasks from the first to the second as they become reliable.

pass@k and pass^k. With n trials of a task and c successes, an unbiased estimate of the chance that at least one of k trials passes is pass@k = 1 − C(n−c, k) / C(n, k). The chance that all k pass is pass^k = C(c, k) / C(n, k). They are equal at k = 1 and move apart as k grows: pass@k rises towards 1 if c > 0, while pass^k falls towards 0 unless c = n.

Isolation and leakage. Each trial needs a fresh environment, or one trial's tickets and memory change the next. Split tasks by family, freeze the final split and record when it is used, as in the RAG course. A suite whose tasks the team has tuned against for months measures that tuning as much as the agent.

Worked example

In the trial fixture, rollback-check passes three of six trials with the default graders. At k = 3, pass@3 = 1 − C(3,3)/C(6,3) = 1 − 1/20 = 0.95, and pass^3 = C(3,3)/C(6,3) = 0.05. The same data describes an agent that almost always succeeds at least once in three tries and almost never succeeds three times in a row. Turning off the step-limit grader lets trial 4 pass (four of six). Whether that is right depends on whether nine steps is acceptable for this task, which is a product decision, not a statistical one.
