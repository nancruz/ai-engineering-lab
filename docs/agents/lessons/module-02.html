Module 02 — Design tools and serve them over MCP

Weeks 5–8 · 3 hours per week · one evolving ops-agent project.

Start here

A model can only be as good as the tools it is given. In this module you replace the lab's tools with your own: clear contracts, validated arguments, structured errors, your retriever as a tool, an MCP server, and side effects that are safe to retry.

Working result: A small tool set with tested contracts, served over MCP to your loop, where every error is structured and no retry can create a duplicate side effect.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/. See the project contract for the tool interface and error codes.

Week 05 — Design tool contracts the model can follow

Write tools the model can choose correctly and call correctly.

Session A — Start and inspect (60 minutes)

Open the tool contract workbench. For each of the five tools, load every argument preset and read the exact error the model would receive. Edit a description to remove “Use before…” and watch the review notes change. Then read tools.json and, for each tool, write one line each for: when to use it, when not to, what it returns and how large the result can be.

Session B — Build or change (60 minutes)

Create one module per tool in app/tools/, each exporting name, description, input_schema, side_effect, approver_roles, timeout_s and run(args, ctx). Validate arguments before run with the lab's schema.py or a JSON Schema library (pin its version). Return the contract's error envelope with a fixed code: invalid_arguments, not_found, forbidden, approval_required, timeout, rate_limited or upstream_error. Keep usage guidance in the tool description, not in the system prompt.

Session C — Run and verify (60 minutes)

Run ten real-model tasks and count invalid calls (unknown tool, schema errors). Improve the descriptions that caused them: add enums, examples of valid values and when-not-to-use lines. Run the same ten tasks again. Keep a change only if invalid calls drop without lowering task success. Add tests asserting that each “should fail” preset from the workbench is rejected with the expected path.

Save: Tool modules, validation tests and the before/after invalid-call counts.

Move on when: every error the model can receive is structured and covered by a test. If the hour ends first, keep your current work and resume the unfinished step next session.

The model calls get_error_ratio with "minutes": "10" (a string). What is the most useful response?

  1. Convert it to 10 silently and run the tool.
  2. Return invalid_arguments with the path and problem, so the model can correct the call and you can count the error.
  3. Raise an exception and end the run.

A structured error lets the model fix the call on the next turn and gives you a number to improve. Silent coercion hides a contract problem; crashing turns a recoverable mistake into a failed task. You can still decide later to coerce specific harmless cases, deliberately and logged.

Week 06 — Turn your retriever into a tool

Give the agent evidence through the same retrieval rules as your RAG service.

Session A — Start and inspect (60 minutes)

Run search_knowledge in the workbench with the “Restricted value” and “Returns untrusted content” presets. Note what the result contains (IDs for citations, status, a trust label, text) and what it leaves out (scores, archived versions). Estimate the tokens one result adds to every later turn.

Session B — Build or change (60 minutes)

Write app/tools/search_knowledge.py around your RAG retriever (projects/knowledge-assistant/ if you built it, otherwise tracks/rag/lab/retrieval.py). Take the caller's role and the current-only rule from the run context, never from model arguments. Cap the output: at most five sources, each text truncated to a fixed length with "truncated": true. Label imported sources trust: "untrusted". When nothing matches, return a message that says what was searched, which helps the model abstain.

Session C — Run and verify (60 minutes)

Add tests: an engineer never receives capacity-private, an admin does, the injection note is labelled untrusted, output size stays under the cap and empty results return the explanatory message. Run credential-policy and orion with the real model and compare them with week 2.

Save: Retrieval tool, authorization and size tests, two comparison runs.

Move on when: authorization tests pass with the role coming only from the run context. If the hour ends first, keep your current work and resume the unfinished step next session.

Why must the caller's role not be an argument of search_knowledge?

  1. It would make the schema too long.
  2. The model writes the arguments, so it could pass any role, including one it was told about by injected text.
  3. Roles change too often to put in a schema.

Anything in the arguments is chosen by the model. Identity and permissions come from the authenticated request that started the run, and the tool applies them itself.

Week 07 — Serve your tools over MCP

Expose the tools through an open protocol so any compatible client can use them.

Session A — Start and inspect (60 minutes)

Read the overview of the current MCP specification (see references): hosts, clients and servers; the tools, resources and prompts a server can offer; the stdio and Streamable HTTP transports; and the date-based version scheme. Create a virtual environment, install the official Python SDK and record the exact version you installed. Run the supplied reference server under the MCP Inspector:

python3 -m pip install "mcp[cli]"
python3 -m pip show mcp            # record this version and pin it
npx @modelcontextprotocol/inspector python3 tracks/agents/lab/mcp_server.py

List the tools, call each with valid and invalid arguments and compare the errors with direct calls.

Session B — Build or change (60 minutes)

Write mcp_server.py in your project, exposing only the read-only tools with the same descriptions and schemas as app/tools/. Log to stderr: stdout carries protocol messages on stdio. Change your loop so it lists tools from the server through the SDK's client and calls them over MCP instead of importing them. Use the client example from the SDK documentation for the version you pinned.

Session C — Run and verify (60 minutes)

Add a test that compares the tool names and input schemas listed over MCP with your local registry. Run credential-policy end to end through MCP. If you already use an MCP-capable desktop or coding assistant, connect it to the same server and call one tool from it.

Save: MCP server, pinned SDK version, registry-parity test, one MCP-backed trajectory.

Move on when: your loop completes a task using tools it discovered over MCP. If the hour ends first, keep your current work and resume the unfinished step next session.

Why keep create_ticket and rollback out of your MCP server for now?

  1. MCP cannot describe tools with side effects.
  2. Any connected client could call them, bypassing the approval gate that lives in your own harness.
  3. They are too slow for the stdio transport.

MCP can expose any tool. Exposing a side-effecting tool means the server itself must authenticate the caller and enforce approval, because you no longer control which client calls it. Module 4 builds that gate first.

Week 08 — Make side effects safe to retry

A retried request must never create a second ticket.

Session A — Start and inspect (60 minutes)

In the action gate workbench, untick “Idempotency keys” and look at “Retry after a timeout”. Then write app/tools/tracker.py: a fictional ticket store with a fault mode that creates the ticket and then times out before replying.

Session B — Build or change (60 minutes)

Make create_ticket require an idempotency_key. Store each key with its fields and result. A repeat with the same key and fields returns the saved result; the same key with different fields returns a conflict error. Classify errors as retryable (timeout, rate_limited, upstream 5xx) or not, and let the harness retry only retryable errors, with backoff and a cap.

Session C — Run and verify (60 minutes)

Tests: create-then-timeout followed by a retry leaves exactly one ticket; same key with changed fields returns conflict; the harness never retries invalid_arguments or approval_required; backoff uses an injectable clock so the test runs instantly.

Save: Tracker, idempotent create, retry policy and the duplicate-prevention tests.

Move on when: no sequence of retries in your tests produces a second side effect. If the hour ends first, keep your current work and resume the unfinished step next session.

The tracker times out after creating a ticket, and the harness retries with a new idempotency key. What happens?

  1. The tracker recognises the retry and returns the first ticket.
  2. A duplicate ticket is created.
  3. The retry fails validation.

The key is what links a retry to the original request. Generate it once per intended action, before the first attempt, and reuse it for every retry.

Reference — concepts used in the experiments

Tool design. A few targeted tools for real workflows usually beat one tool per API endpoint. Give similar tools distinct, namespaced names. Return only what the model needs to decide the next step, with IDs it can cite, and keep results short because every result is re-read on every later turn. Errors should say what was wrong and how to fix it. Descriptions are prompts: test changes to them like any other prompt change.

Schemas. JSON Schema describes argument types, required fields, enums, lengths and patterns. Set additionalProperties: false so invented arguments are rejected. Some providers offer a strict mode that constrains generation to the schema; still validate on your side, because schema-valid is not the same as allowed. An invented approval_id can match the pattern and still have no approval behind it.

MCP. The Model Context Protocol separates a host application (with one or more clients) from servers that offer tools (called by the model), resources (data the application chooses to load) and prompts (templates a user picks). Versions are dates; the specification revision current at the time of writing is 2026-07-28, which made requests self-contained instead of relying on a session handshake. SDKs lag and lead the specification at different times, so pin the SDK version and read its changelog before upgrading.

Idempotency. An operation is idempotent if repeating it has the same effect as doing it once. Networks make “did it happen?” unknowable after a timeout, so side-effecting tools need a client-generated key the server uses to deduplicate. Drafting first and committing later also gives a person a place to approve the exact fields.

Worked example

In the workbench, the rollback preset “Approval from the model, not a person” sends approval_id: "A-1". The schema accepts it: the pattern matches. The gate refuses it: no approval record with that ID exists. Validation answers “is this well-formed?”; authorization answers “is this allowed?”. You need both, in that order, and neither can be delegated to the model.
