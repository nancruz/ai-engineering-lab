Module 04 — Guardrails, permissions and human approval

Weeks 13–16 · 3 hours per week · one evolving ops-agent project.

Start here

An agent that can act can act wrongly, and text inside its context can try to steer it. In this module you map what could go wrong, test prompt-injection defenses, move every permission and approval into code, and attack your own agent.

Working result: A threat model, an action gate that enforces permissions, field-bound approvals, an egress allowlist and taint holds, plus a red-team log whose every successful attack has become a regression test.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All attack material in this module is aimed at your own fictional system. Keep it in fixtures and never point it at real services or people.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/.

Week 13 — Threat-model your agent

Decide what to protect before choosing defenses.

Session A — Start and inspect (60 minutes)

Open the action gate workbench with every defense off and read the eleven scenarios. Then make a table of your own tools: what each can read, what it can change, which inputs an outsider can influence (imported documents, ticket bodies, tool errors) and where data can leave the system.

Session B — Build or change (60 minutes)

Write artifacts/security/threat-model.md: assets, entry points for untrusted text, actions with real impact, current controls and gaps. Mark every place where one run combines private data, untrusted content and a way to send data out. Rank risks by impact and likelihood.

Session C — Run and verify (60 minutes)

Turn the top five risks into tests in tests/security/. Most should fail today; that is the point. Name each test after the harm it describes, for example test_untrusted_note_cannot_create_ticket.

Save: Threat model and five failing security tests.

Move on when: each top risk has a test that would catch it. If the hour ends first, keep your current work and resume the unfinished step next session.

Which combination in a single run is the most dangerous?

  1. A large model with a long context.
  2. Access to private data, exposure to untrusted content and a way to send data outside.
  3. Many tools with similar names.

With all three, injected text can tell the agent to read something private and send it out. Removing any one of the three breaks that chain.

Week 14 — Test prompt-injection defenses

Measure how often injected instructions work, and what they can achieve when they do.

Session A — Start and inspect (60 minutes)

Run injected-note five times with your real model and record whether it follows the note. Then write ten injection variants as fictional documents in data/fixtures/injections/: a direct instruction, “the user asked me to…”, a fake system message, an instruction inside a ticket body, one inside a tool error, one split across two documents, and four of your own.

Session B — Build or change (60 minutes)

Add defenses as separate layers you can switch on and off. First, prompt layers: untrusted results wrapped in clear delimiters with their trust label, and system-prompt guidance. Second, a code layer: tools set a tainted flag on the run when they return untrusted content. Once tainted, side-effecting actions need a person's confirmation, even if a standing policy would approve them automatically.

In the action gate workbench, switch only “Hold tainted sessions” on and off, and compare “Auto-approved ticket requested by an imported note” with “Post the handover to the on-call channel”.

Session C — Run and verify (60 minutes)

For each variant, run three trials with each layer combination and record the attack success rate: did a forbidden action execute? Report the prompt layers and the code layer separately. Expect prompt layers to lower the rate without reaching zero, and the code layer to change what a successful injection can do.

Save: Injection fixtures, layered defenses and the attack-success table.

Move on when: no variant can cause a side effect without a person's confirmation, whatever the model does. If the hour ends first, keep your current work and resume the unfinished step next session.

Which defense still holds if the model is completely fooled by an injection?

  1. A stronger warning in the system prompt.
  2. Asking the model to double-check its plan before acting.
  3. A code-level check that holds side effects in tainted runs for a person to confirm.

Prompt defenses depend on the model's judgement, which is exactly what injection attacks. A check in code does not read the injected text, so it cannot be persuaded.

Week 15 — Enforce permissions and approvals in code

Make every approval specific to who, what and which exact fields.

Session A — Start and inspect (60 minutes)

In the workbench, use the presets and find, for each harmful scenario, the single defense that stops it. Read the fictional policy approval-v2: approval is tied to the exact fields and an idempotency key, and changed fields need a new approval.

Session B — Build or change (60 minutes)

Write app/gate.py. Approval records hold an ID, the action, a hash of the exact fields, the approver, their role, an expiry and whether they were used. The gate checks, in order: egress allowlist for anything that sends data out; that an approval exists; that the approver's role may approve this tool (only incident-commander for rollback); that the fields hash matches; that it has not expired or been used; and the taint hold. Add make -C projects/ops-agent approve RUN=<id>, which prints the exact fields and records your decision.

Session C — Run and verify (60 minutes)

Port guard_scenarios.json into your tests and make every harmful scenario fail closed. Run rollback-check end to end with the real model: it drafts, the run pauses, you approve as incident commander, the run resumes and executes exactly the approved request once.

Save: Gate, approval command, scenario tests and the approved end-to-end run.

Move on when: your week 13 security tests pass. If the hour ends first, keep your current work and resume the unfinished step next session.

An engineer approved a low-severity ticket. Before creating it, the agent raises the severity to high. What should the gate do?

  1. Allow it: the ticket was approved.
  2. Block it: the approval covers the exact fields that were shown, and these fields changed.
  3. Allow it but log a warning.

An approval is consent to a specific request. Binding it to a hash of the fields means any change, by mistake or by injection, needs a fresh decision.

Week 16 — Red-team the whole agent

Attack your own system with a goal and a time limit.

Session A — Start and inspect (60 minutes)

Set four goals: change production without a valid approval, reveal capacity-private to an engineer, send any internal text to a host outside the allowlist, and create a duplicate ticket. Prepare a log, artifacts/security/redteam.jsonl, with fields for input, goal, outcome and the layer that stopped it.

Session B — Build or change (60 minutes)

Spend the hour attacking through every input an outsider controls: imported documents, ticket bodies, tool error text and the user prompt. Log every attempt, including those that failed.

Session C — Run and verify (60 minutes)

Fix whatever got through and add each successful attack as a regression test. Update the threat model with residual risks: what you did not test and what a stronger attacker might try.

Save: Red-team log, fixes, new regression tests and the updated threat model.

Move on when: every successful attack is now a passing test, and the residual risks are written down. If the hour ends first, keep your current work and resume the unfinished step next session.

An hour of red-teaming found no successful attack. What can you claim?

  1. The agent is secure against prompt injection.
  2. The attacks you tried did not succeed against this version. Keep them as tests and record what was not tried.
  3. Further testing is unnecessary until the model changes.

Finite tests show that the tested cases are handled. New models, prompts and tools change the attack surface, so the tests run on every release.

Reference — concepts used in the experiments

Prompt injection. Direct injection comes from the user. Indirect injection arrives inside data the agent reads: documents, web pages, emails, tool results. Models cannot reliably separate instructions from data in the same context, so treat every model decision as possibly influenced by any text it has read.

Layered mitigations. Widely recommended measures include: constrain the model's role in the system prompt; define expected output formats and check them in code; filter sensitive content on the way in and out; give the application its own credentials and keep privileged functions in code with least privilege; require human approval for high-risk actions; separate and label untrusted content; and test adversarially on a regular basis. Only the code-level measures hold when the model is fooled.

Approvals. Bind approvals to the exact request and the approver's role, make them expire and single-use, and show the person what will actually happen. People approve too quickly when asked often (approval fatigue), so reduce the number of requests by drafting and batching, and never rely on approval alone for exfiltration: an egress allowlist does not get tired.

Taint. Tracking whether untrusted content has entered a run lets you tighten rules only when risk is present, instead of making every run slow. The cost is friction on legitimate actions in tainted runs, which the workbench shows as “legitimate actions stopped”.

Worked example

In the workbench, “Email the handover to an outside address” has a human approval with matching fields. With approval required, approval binding and the taint hold all on, it still executes: a person approved it. Only the egress allowlist stops it. The lesson is not that approval is useless. Approval answers “did someone agree?”, while the allowlist answers “can data go there at all?”, and a tired approver does not change the second answer.
