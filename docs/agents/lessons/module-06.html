Module 06 — Orchestrate multiple agents and adopt a framework

Weeks 21–24 · 3 hours per week · one evolving ops-agent project.

Start here

Many job descriptions mention multi-agent systems and agent frameworks. This module gives you first-hand evidence about both: you split a task across worker agents, define what they hand to each other, rebuild part of the agent in a framework, and then decide with numbers what to keep.

Working result: An orchestrator–worker version of the handover task with validated hand-offs, a framework port of two tasks, and a decision record comparing them with your single-agent loop on the same suite.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/.

Week 21 — Split a task across worker agents

Try separate contexts on a task that has independent parts.

Session A — Start and inspect (60 minutes)

Take the long handover task from Module 3 and mark which parts are independent: policy lookup, metrics per service, recent changes. Read the reference section on when multi-agent designs help and when they waste tokens. Write down what you expect to happen to success, tokens and wall time.

Session B — Build or change (60 minutes)

Write app/orchestrator.py. A lead agent produces a structured plan of subtasks. Each subtask runs in a worker with its own context, a restricted, read-only tool set and its own budget. Workers run in parallel and return condensed results. Only the lead may draft, and no worker can reach a side-effecting tool.

Session C — Run and verify (60 minutes)

Run the handover family three times each with the single agent and with the orchestrator. Compare success, total tokens, wall time and the largest context any one agent saw. Compare the numbers with what you expected in session A.

Save: Orchestrator, worker tool restrictions and the comparison table.

Move on when: you have measured both designs on the same tasks with the same number of trials. If the hour ends first, keep your current work and resume the unfinished step next session.

What is the main benefit of giving each worker its own context?

  1. Each worker becomes a more capable model.
  2. Each works in a small, focused context and returns a condensed result, so the lead's context stays small.
  3. It reduces the total number of tokens used.

Separate contexts help with focus and parallelism, but total tokens usually go up because every worker has its own instructions and reads its own results. Measure whether the gain is worth that cost.

Week 22 — Define hand-off contracts

Make what passes between agents as checkable as a tool result.

Session A — Start and inspect (60 minutes)

Read the worker outputs from week 21. Look for prose results with missing numbers, and for places where the lead stated a detail no worker reported. Note each one as a contract gap.

Session B — Build or change (60 minutes)

Define two schemas. An assignment has an objective, inputs, allowed tools, an output schema and a budget. A result has findings, each with source IDs, plus unknowns and tokens used. Validate both directions and retry a worker once on an invalid result. Propagate taint: if a worker read untrusted content, the lead's run becomes tainted too. Link worker trajectories to the lead with a parent run ID.

Session C — Run and verify (60 minutes)

Tests: an invalid worker result is rejected and retried once, then reported as unknown; a worker's taint reaches the lead; each worker's budget is enforced; the lead's final answer cites only finding IDs the workers returned. Re-run the handover family and compare it with week 21.

Save: Hand-off schemas, validation, taint propagation and the re-run.

Move on when: every claim in the lead's answer traces back to a worker finding with a source. If the hour ends first, keep your current work and resume the unfinished step next session.

A worker read the imported note, and the lead summarises that worker's result. What must happen?

  1. Nothing: the lead never saw the note itself.
  2. The lead's run becomes tainted, because untrusted text may have shaped the worker's result.
  3. The worker's result is discarded.

Injected instructions can survive summarisation. Taint must follow the data across agent boundaries, or splitting the work becomes a way around the gate.

Week 23 — Rebuild the agent in a framework

Learn what a framework gives you, and what it hides.

Session A — Start and inspect (60 minutes)

Pick one agent framework that job descriptions you are interested in mention, for example LangGraph, the OpenAI Agents SDK, the Claude Agent SDK or PydanticAI. Read its current documentation and pin the version. Map your own parts onto it: loop, tools, budgets, gate, checkpoints and traces. Note anything without an obvious equivalent.

Session B — Build or change (60 minutes)

Rebuild credential-policy and rollback-check in the framework under app/framework_port/. Reuse your tool modules and keep your gate in the path of every side effect. Do not port everything; two tasks are enough to compare.

Session C — Run and verify (60 minutes)

Run your eval suite for those two families against both implementations, three trials each. Compare success, tokens, how much code you own, what the framework does that you did not ask for (extra prompt text, automatic retries, parallel calls) and how you inspect a run. Write artifacts/decisions/002-framework.md.

Save: Framework port, comparison and decision record.

Move on when: you can name every behaviour the framework adds and show where it appears in a trace. If the hour ends first, keep your current work and resume the unfinished step next session.

The framework retries failed tool calls automatically. What is the risk?

  1. Runs take slightly longer.
  2. A side-effecting call retried without an idempotency key can happen twice.
  3. The model sees fewer errors.

Framework defaults are design decisions someone else made. Find them, then either configure them or make your tools safe under them.

Week 24 — Keep, simplify or drop the extra agents

Decide on evidence, then leave the codebase in the chosen shape.

Session A — Start and inspect (60 minutes)

Collect the numbers from weeks 21–23 into one table: pass^3 per family, cost per success, latency, lines of code you own, and how long it took you to debug the last failure in each version.

Session B — Build or change (60 minutes)

Write artifacts/decisions/003-architecture.md: single agent or orchestrator, own loop or framework, and for which task families. Include what would change your mind, for example a new task family that is highly parallel.

Session C — Run and verify (60 minutes)

Apply the decision: remove what you are not keeping or put it behind a configuration switch. Make sure the release gate and eval suite cover whatever remains, and update your copy of the project contract.

Save: Architecture decision, cleaned-up code and a passing gate run.

Move on when: the shipped design is the one your numbers support and the gate covers it. If the hour ends first, keep your current work and resume the unfinished step next session.

The orchestrated version is 3 points more successful, uses 4× the tokens and is 40% faster. What do you do?

  1. Ship it: success went up.
  2. Drop it: tokens went up.
  3. Decide from what the task is worth and how much latency matters, write the trade-off down with these numbers, and check that the 3 points are larger than run-to-run noise.

Architecture choices are trade-offs. A small gain may be noise; a 4× cost may be fine for a rare, valuable task and wrong for a frequent, cheap one.

Reference — concepts used in the experiments

When multiple agents help. Separate agents help when a task breaks into independent parts that each need a lot of reading (wide research, several services to check), when parts need different tools or permissions, or when one context would overflow. They are a poor fit when every part needs the same shared context, when parts depend tightly on each other, or when the task is not valuable enough to justify the extra tokens. Published experience reports multi-agent systems using many times more tokens than a chat interaction, so measure cost per success, not success alone.

Hand-offs. Treat messages between agents like API calls between services: a schema, validation, a budget, an error path and a trace ID. Prose hand-offs lose numbers and invite the next agent to fill gaps with guesses.

Frameworks. Frameworks package the loop, tool registration, state, tracing and multi-agent patterns. They save code and add defaults: prompt text, retries, concurrency, memory. Pin versions, read the changelog, and keep anything security-relevant (approval gate, permissions, egress) in code you own and test.

Worked example

A metrics worker returns “playback error ratio is high”. The lead writes “above 2 percent for five consecutive minutes, so rollback is justified”. No worker reported that. With a result schema that requires the points and a source ID for every finding, and a rule that the lead may cite only finding IDs, the same run produces “the metrics worker returned no per-minute data; the condition is unverified”. That answer is less satisfying and correct.
