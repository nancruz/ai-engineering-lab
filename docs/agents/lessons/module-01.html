Module 01 — Build and inspect an agent loop

Weeks 1–4 · 3 hours per week · one evolving ops-agent project.

Start here

You start with the supplied lab: a working loop, fictional tools and two scripted models that behave the same way every time. You read it, change it, then write your own loop against a real model and give it explicit ways to stop.

Working result: Your own loop, running a real tool-calling model against the fictional tools, that always stops for a named reason and saves a trajectory you can read line by line.

Read only the current week's instructions. Use the reference section when a step points to a concept. Show progress with working code, saved runs, tests and short notes attached to a change; there are no written theory answers. Quick checks are for you and are never graded.

All shell commands start at the repository root. Paths beginning with app/, configs/, data/, tests/ or artifacts/ mean files inside projects/ops-agent/, which you create in week 1. The supplied reference stays in tracks/agents/lab/. See the project contract for the directory map, interfaces and commands.

Week 01 — Run and trace the supplied agent

See every moving part of an agent before you write one.

Session A — Start and inspect (60 minutes)

Run the lab's tests, then run one task and read the whole trace:

python3 -m unittest discover -s tracks/agents/lab -p 'test*.py' -v
python3 tracks/agents/lab/run.py --task rollback-check

For each step, note what the model asked for, what came back and how large the context estimate became. Then open agent.py and find run_agent. Mark the four lines that matter: where the model is called, where the tool runs, where the result is appended and where the loop ends.

Open the agent loop workbench and press “Next step” four times. Open “What the model reads” after each step and watch the message list grow.

Session B — Build or change (60 minutes)

Create projects/ops-agent/ with the directories from the project contract. Run all four tasks and save each record:

mkdir -p projects/ops-agent/artifacts/runs/week-01
for t in credential-policy rollback-check orion injected-note; do
  python3 tracks/agents/lab/run.py --task $t --out projects/ops-agent/artifacts/runs/week-01/$t.json
done

Open one saved file and find the fields you will need later: stop_reason, side_effects, drafts, checks and each step's context_tokens.

Session C — Run and verify (60 minutes)

Change one option at a time and predict the outcome before each run. Write the prediction down first.

python3 tracks/agents/lab/run.py --task rollback-check --model scripted:eager
python3 tracks/agents/lab/run.py --task rollback-check --model scripted:eager --no-gate
python3 tracks/agents/lab/run.py --task orion --model scripted:eager --no-repeat-check
python3 tracks/agents/lab/run.py --task rollback-check --fault timeout_once --no-retry

For each run, record the stop reason, any side effects and which checks failed. Where your prediction was wrong, find the line in agent.py that explains it.

Save: Four baseline trajectories and a short notes file with your predictions and what actually happened.

Move on when: you can point to the code that ended each run and explain it from the saved record alone. If the hour ends first, keep your current work and resume the unfinished step next session.

In the supplied lab, where is the decision made that rollback needs an approval?

  1. In the system prompt, which tells the model not to change production.
  2. In Env.call, before the tool runs, by checking for an approval record.
  3. In the scripted model, which chooses not to call rollback.

The eager model does call rollback. It is the harness check in Env.call that returns approval_required. The system prompt asks; the code enforces.

Week 02 — Write your own loop against a real model

Replace the scripted model with a real one and write the loop yourself.

Session A — Start and inspect (60 minutes)

Follow Connect a real tool-calling model and choose the local route or the cloud route. Run the supplied adapter once on the simplest task and save its raw responses:

python3 tracks/agents/lab/run.py --task credential-policy --model ollama:<your-tag> \
  --out projects/ops-agent/artifacts/runs/week-02/supplied-credential.json

Open model_log in the saved file. Find the provider's tool-call structure, the token counts and how the final answer is marked. Record the exact model tag or ID and provider version.

Session B — Build or change (60 minutes)

Write app/models/<provider>.py and app/loop.py following the contract interfaces. The adapter converts your neutral message list into the provider's format and returns tool_calls, text, stop_reason and usage. The loop executes every tool call in a turn and appends one result per call, matched by call ID. Import the supplied Env for the tools for now; you replace them in Module 2.

Write one JSON line per event to artifacts/runs/<run-id>/trajectory.jsonl, using provider token counts instead of the lab's estimate.

Session C — Run and verify (60 minutes)

Add tests/test_loop.py with a scripted stub model (no network): one turn that requests two tool calls, then a final answer. Assert that two results are appended with the right IDs and that the loop stops on the answer. Then run all four tasks once with the real model and compare each with its week 1 baseline: which succeeded, and where did the steps differ?

Save: Loop, adapter, the offline unit test and four real trajectories.

Move on when: the test passes without network access and one real trajectory shows a tool call, its result and a final answer in order. If the hour ends first, keep your current work and resume the unfinished step next session.

The model returns two tool calls in one turn. What must the harness send back before the next model call?

  1. Only the first result; the model will ask again for the second.
  2. One result for each call, each referencing that call's ID.
  3. Both results joined into a single text message.

Providers pair each result with its request by ID. Missing or merged results either fail validation or leave the model guessing which output belongs to which call.

Week 03 — Add budgets and stop rules

Make sure every run ends, and ends for a reason you can name.

Session A — Start and inspect (60 minutes)

In the workbench, run the orion task with the eager model and repeat detection off. Watch the context grow while nothing new is learned. Then run orion three times with your real model and record turns, tokens and whether it abstained.

Open orion with the eager model, untick “Repeat detection” and press “Run to the end”.

List the stop conditions your loop needs: final answer, maximum turns, maximum total tokens, wall-clock timeout, repeated identical calls and consecutive tool errors.

Session B — Build or change (60 minutes)

Put the limits in configs/agent.json and enforce them in the loop. Every run writes exactly one stop_reason into its summary. Copy the lab's repeat rule: block an identical call unless it is a single retry of a transient error. When a budget ends the run, return a partial result that says what was done and what is still unknown, not an empty failure.

Session C — Run and verify (60 minutes)

Write one test per stop reason using stub models: one that always calls the same tool, one that never answers, one facing a tool that always times out. Assert the summary names the right reason. Run orion with the real model and max_turns=3, then read the partial result.

Save: Budget configuration, stop-reason tests and one partial-result example.

Move on when: every run ends with one of a fixed set of stop reasons, and each reason has a test. If the hour ends first, keep your current work and resume the unfinished step next session.

You block every repeated identical tool call. What breaks?

  1. Nothing; repeated calls are always a mistake.
  2. A legitimate retry after a transient timeout is blocked too.
  3. The context grows faster.

A repeat is wasteful only when the earlier result is still valid. After a timeout the same call is the right next step, once. The lab allows exactly one retry of a retryable error.

Week 04 — Decide between a workflow and an agent

Measure whether the model needs to choose the steps at all.

Session A — Start and inspect (60 minutes)

Write rollback-check as a fixed workflow in app/workflows/rollback.py: search the policy, read the metrics, compute the condition in code, draft if it is met, and use the model only to write the summary. List every decision that moved from the model into code.

Session B — Build or change (60 minutes)

Create data/tasks/dev.jsonl with five rollback cases: condition met (playback), condition not met (catalog), metrics timing out, the question phrased differently, and a user asking you to “just roll it back”. Run the workflow and the agent three times on each case.

Session C — Run and verify (60 minutes)

Tabulate success, turns, tokens and wall time per case for both versions. Write artifacts/decisions/001-workflow-or-agent.md: which version you keep for which case, with the numbers. Keep both implementations; Module 5 measures them again on a larger suite.

Save: Workflow, dev cases, comparison table and decision record.

Move on when: the decision cites measured differences on the same cases, whichever way it goes. If the hour ends first, keep your current work and resume the unfinished step next session.

When is a fixed workflow usually the better choice?

  1. Whenever the task has more than one step.
  2. When the steps are known in advance and the same for every input.
  3. When you want the model to be more creative.

Fixed steps are cheaper, faster and easier to test. Let the model choose when the next step depends on what the last one returned, or when there are too many paths to write by hand.

Reference — concepts used in the experiments

Messages and tool calls. Provider APIs represent a tool request as a structured block with an ID, a tool name and JSON arguments. The response's stop reason tells you whether the model wants tools run or has finished. Your harness sends each result back referencing the request ID. Some models request several tools in one turn (parallel tool calls); run them, or explicitly refuse the extras, but never drop them silently.

Why budgets. Each turn re-reads the whole context, so the cost of a run grows faster than its number of steps. Models also loop: they repeat a search hoping for a different answer, or alternate between two tools. A turn limit stops runaway cost; it does not fix the behaviour. Repeat detection, better tool results (for example “no source mentions ORION”) and clear stop instructions do.

Workflows and agents. Common workflow patterns include prompt chaining (fixed sequence), routing (classify, then pick a path), parallelization (independent calls whose results are combined), orchestrator–workers (a model splits work for other calls) and evaluator–optimizer (one call critiques another's output). An agent is the open-ended case where the model chooses tools until it decides it is done. Start with the simplest design that passes your cases and add autonomy only where measurements show it helps.

Non-determinism. Sampling means the same input can produce different trajectories. Lowering temperature reduces variation but does not remove it, and provider-side changes can alter behaviour. Record model ID, parameters and prompt version with every run so differences can be traced.

Worked example

With the eager model and no repeat detection, orion issues the same search six times. The context grows from about 100 to about 1,100 estimated tokens and the run ends on the turn budget with no answer. With repeat detection on, the second identical search is refused with a message telling the model to change approach or answer; it abstains on turn 3. The budget limited the damage, but repeat detection changed the outcome.
