COURSE MATERIAL

Practical checkpoints

Progress is shown by working behaviour and reproducible artifacts. Quick checks in the lessons help you test your understanding; they are not graded and do not count here. Use each session's “Move on when” line; if it is not met, keep working there within the weekly budget.

Completion checkpoints

After modulePractical check
1Run your own loop with a real model on all four lab tasks; show a test for every stop reason and the workflow-or-agent decision with numbers.
2Complete a task using tools discovered over MCP; show the before/after invalid-call count and a retry that does not duplicate a ticket.
3Kill a long run halfway, resume it, and reach the same end state with no duplicate side effect; show the context breakdown before and after compaction.
4Show that no injection variant causes a side effect without a person, that changed fields invalidate an approval, and the red-team log with its regression tests.
5Seed a regression and watch the release gate block it; show pass^k per family from at least three trials.
6Show the architecture decision with cost per success, pass^3 and latency for each option on the same suite.
7Operate the deployed pilot: flip the kill switch, roll back a release manifest and resume a paused run; explain one run's cost from its trace.

A failed experiment can be complete: a measured “the orchestrator was not worth it” is a result. A broken implementation hidden behind a confident write-up is unfinished. Finite security tests demonstrate their tested cases, not general resistance to attack. Keep known limitations visible.

Consolidation weeks

After modules 2, 4 and 6, take a week without new material if you need it: finish any unmet “Move on when” checks, tidy your decision records and re-run the full test suite. This is optional; the session tracker does not count these weeks.

Turning the project into interview evidence

  • A one-page README in projects/ops-agent/: what it does, the architecture figure from Module 7, how to run check, eval and gate.
  • Three decision records with numbers: workflow or agent, framework, architecture.
  • The threat model and red-team log, with residual risks stated plainly.
  • One reliability report showing pass@k against pass^k, and one cost-per-success comparison.
  • A short trace walkthrough: one run explained from its spans.
