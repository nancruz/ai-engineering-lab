RAG / Run the first real model

COURSE MATERIAL

Run the first real model

Use this in Module 1, week four. Earlier scripts only retrieve and evaluate. This session adds a real generator and saves its exact evidence and response.

Default local route

  1. Install Ollama using its official download/setup instructions. Start the local service. Keep it on localhost.
  2. Download the starter model in a terminal:
ollama pull llama3.2:3b
ollama list
  1. Record the actual tag/digest and installation version. A 3B-class model still needs suitable RAM/storage; download/setup and cold-start time count toward your session. If unavailable or too slow, use the cloud alternative below and record the difference. Check the starter model card and license when installing.
  2. At repository root, run:
python3 tracks/rag/lab/answer.py --question-id q02 --model llama3.2:3b --out projects/knowledge-assistant/experiments/module-01/answer-q02.json

The script retrieves current authorized candidates using BM25, sends their text and IDs to Ollama's /api/chat, requests nonstreamed JSON and validates its structure/citation IDs. It saves question, prompt, context, requested model, raw provider metadata and parsed output. It never uses reference evidence labels to choose the answer.

  1. Open the saved file and check the answer against evidence. A schema-valid answer can still be wrong. q02 should be checked against the current 800-millisecond policy, not against text generated by another model.
  2. Repeat with --question-id q13 and q16, changing the output filename each time. Check completeness and whether the model abstains where evidence is insufficient.

What a failure means

Symptom Next action
Connection refused Start Ollama and confirm its localhost port; do not change retrieval code.
Model not found Check ollama list and pull/select an installed compatible tag.
Slow first response Separate loading time from warm inference; use the bounded timeout and record actual hardware.
Invalid JSON or unknown citation Open the saved result: validation_error describes the failure and provider_response preserves the raw output. Validation is doing its job. Do not fabricate a successful response.
Correct-looking answer, wrong fact Inspect selected evidence and claim support; valid structure does not establish truth.
No matching eligible results The supplied script abstains without calling a model. Record this separately from model-generated abstention.

The fixture reader role is not authenticated. This script uses fictional data and is a local learning tool. Its citation checks constrain output shape; they do not establish semantic grounding or production security.

Cloud alternative if local hardware is unsuitable

Use the Bedrock adapter example in the AWS guide behind the same generate(messages, settings) interface. Install boto3 in your project environment, authenticate through your own AWS SSO profile, select a Converse-compatible model available in your account/region and bound output tokens and call count. Keep the same evidence selection and JSON validation used by the local example.

This alternative requires implementing a small adapter before the first call. Record the provider/model and the extra setup time. No paid calls, AWS accounts or permissions are provisioned for you by the course. Stop setup at the session limit and resume; a recorded fixture is not a substitute for completing a real model call.

Reference

Ollama chat API documents messages, JSON output and nonstreaming responses. The course helper is a small example around that API, not a complete provider resilience layer. Timeouts, retry policy and provider substitution are developed in Module 3.
