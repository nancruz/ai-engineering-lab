Better retrieval, proven with numbers

The three upgrades most production RAG systems use: combine keyword and vector search, rerank a shortlist with a more careful model, and rewrite the question before searching. Each costs latency and money, so you'll keep only what your evaluation says is worth it.

LEARN

Fuse, rerank, rewrite

Hybrid search: merge rankings, not scores

Module 2 showed that BM25 and vectors fail on different questions, so run both. The catch is merging. A BM25 score of 7.8 and a cosine of 0.49 aren't on the same scale, and adding them is meaningless. Reciprocal rank fusion (RRF) ignores scores and uses positions only:

rrf(d) = Σ over rankings that contain d of 1 / (c + rank(d)) with c = 60 by default

A document near the top of either list gets a good score; one near the top of both gets the best. The constant c controls how much being first matters compared with merely being present.

Reranking: a second, slower opinion

A reranker reads the question and a passage together, so it can notice that "search requests use a 1200 ms deadline" doesn't answer a question about the catalog, even though the words overlap. That's far more precise than comparing two independent vectors, and far slower: one model call per (question, passage) pair. So it's always a second stage: retrieve ~20 candidates cheaply, rerank them, keep the top 5. Options: a small trained cross-encoder such as ms-marco-MiniLM-L6-v2 (fast, local), a hosted rerank API, or an LLM asked to grade each passage (flexible, slowest).

Reranking can only reorder what retrieval found. If the right passage isn't among the candidates, no reranker can bring it back. Check evidence found at the candidate depth (say k = 20) before blaming the reranker.

Rewriting the question

Users don't write the way documentation does. Before searching, an LLM can:

  • Multi-query: rephrase the question 3 ways, search with each, and fuse the results with RRF. Cheap insurance against vocabulary mismatch.
  • HyDE (hypothetical document embeddings): write a fake answer and search with that, since a fake runbook paragraph looks more like the real runbook than a question does.
  • Condense a conversation: turn "and in staging?" into "What is the rollback approval rule in staging?" using the chat history. Any chat assistant needs this.

Each adds an LLM call, so roughly 0.5–2 seconds, before retrieval even starts.

Key takeaways

  • Hybrid search covers both exact terms and paraphrases; fuse ranks with RRF because scores aren't comparable.
  • Rerank a shortlist with a model that reads question and passage together; it can't recover missed passages.
  • Query rewriting fixes vocabulary mismatch at the cost of an extra model call.
  • Every stage costs latency: keep it only if your evaluation improves.

Lab 6: fusion, reranking and multi-query

Goal: add hybrid, reranked and multi-query retrieval behind the same interface, and decide with eval which ones your system keeps.

You write: minirag/hybrid.py → rrf · minirag/rerank.py → rerank, parse_score · minirag/query.py → parse_queries. Supplied: HybridRetriever, RerankRetriever, MultiQueryRetriever and the reranker adapters.

  1. Reciprocal rank fusion

    rrf(rankings, c): add 1 / (c + rank) for every id in every ranking (ranks start at 1; an id repeated within one ranking counts once), then sort by score and id. HybridRetriever calls it with the BM25 and dense rankings.

    $ python3 -m unittest -v tests.test_lab6_retrieval -k Fusion

  2. Rerank

    rerank(query, hits, reranker, top_n): score all candidate texts in one reranker.score call, sort by the new score (keep the original order for ties), return the top top_n with their new scores. parse_score turns an LLM reply like "Score: 7/10" into 7.0.

    $ python3 -m unittest -v tests.test_lab6_retrieval -k Rerank

  3. Multi-query

    parse_queries(text, original, n): clean the LLM's list of rewrites (strip numbering, bullets and quotes, drop blanks and duplicates) and return the original first, then up to n rewrites.

    $ python3 -m unittest -v tests.test_lab6_retrieval

  4. Compare

    Use k = 3 so differences show:

    $ python3 -m minirag eval --compare bm25,dense,hybrid,hybrid+rerank --k 3
    retriever               hit@k  recall    MRR   nDCG  evidence  tokens   leaks
bm25                     0.96    0.94   0.90   0.90      0.82     202   0
dense                    1.00    0.94   0.91   0.89      0.76     204   0
hybrid                   1.00    0.98   0.94   0.94      0.86     216   0
hybrid+rerank            0.96    0.92   0.87   0.87      0.82     228   0

    Hybrid beats either retriever alone, even with the weak offline embedder. The default reranker, overlap, is a toy that counts shared words, and it makes things worse. A stage that sounds like an improvement can be a regression; this table is how you find out.

    Look for: evidence and MRR against the extra time. eval --answers prints timings per question in the saved --out file.
  • Multi-query on paraphraseseval --compare bm25,bm25+multiquery --type paraphrase --llm ollama:llama3.2:3b
    Look for: whether rewrites help BM25 close the gap with vectors on paraphrase questions, and what they do to exact-code questions (--type exact).
  • Fusion depth and cChange HybridRetriever(depth=20, c=60) in retrieval.py to depth 5 and 50, and c to 1 and 200.
    Look for: small changes. RRF is robust to its settings, which is a big part of why it's the default.
  • HyDEquery.py has hyde_query(). Wire it into a retriever that searches with the hypothetical answer (copy MultiQueryRetriever as a template) and evaluate it with a real embedder.
    Look for: questions where the fake answer invents details that pull in the wrong documents.
