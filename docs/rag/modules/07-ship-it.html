From script to service

A RAG system in production is two programs: an indexing job that keeps chunks and vectors in sync with the documents, and an API that answers questions safely, quickly and observably. You'll build both, put them in a container, and work out what a question costs.

Production RAG has two paths

Keep the index in sync

Documents change every day. Re-embedding everything on every change is slow and, with a hosted embedding API, expensive. Instead, store a fingerprint (a hash of the document's text, metadata and your chunking and embedding settings) per document. On each run:

  • new fingerprint for a known document → delete its old chunks, insert the new ones, embed only those;
  • same fingerprint → skip it;
  • document gone from the source → delete it and its chunks. Deletions are the step teams forget, and how a "deleted" policy keeps answering questions for months.

Changing the chunk size or embedding model changes every fingerprint, so everything is rebuilt: exactly what should happen. Larger systems build a new index next to the old one and switch an alias when it's complete, so a half-built index never serves traffic.

An API contract you can operate

ConcernWhat the service does
InputReject missing, blank or oversized questions with 400. Bound k. Limits protect your budget as much as your server.
IdentityUnknown or missing role → 401. Here the role comes from a header for simplicity; a real deployment takes it from a verified token (OIDC/JWT), never from what the client claims.
DependenciesModel provider down → 502 with a request id. Anything else → 500 "internal error", with no stack trace or hostnames in the response.
TraceabilityEvery response carries a request_id; every request, including failures, writes one trace line with that id.

Observe what matters

Log, per request: role, question length (not the text, which may be personal data), retrieved chunk ids, cited document ids, whether it abstained, and time per stage. With that you can answer the questions on-call actually asks: "why did it say that?", "is it slower since Tuesday?", "which documents never get cited?". Sample real questions, with the right permissions, to grow your evaluation set.

Two things usually surprise people: retrieval is a rounding error next to generation time, and the retrieved chunks, repeated on every question, are a large share of the bill. Halving k or the chunk size is often the cheapest optimization you'll find, if your evaluation agrees.

Key takeaways

  • Separate indexing from serving; sync incrementally with fingerprints, and propagate deletions.
  • Validate input, take identity from a trusted source, map failures to clear status codes, never leak internals.
  • Trace every request with ids and per-stage timings, without logging sensitive text.
  • Generation dominates latency; retrieved context drives cost.

Lab 7: a persistent index and an API

Goal: run your RAG system as a service: an index that re-embeds only what changed, an HTTP API with validation, error mapping and traces, packaged in a Docker image.

You write: minirag/store.py → IndexStore.sync · minirag/service.py → RagService.handle_ask. Supplied: the schema, the FastAPI and standard-library HTTP adapters, the Dockerfile.

  1. Incremental sync

    IndexStore.sync(docs, strategy, size, overlap, embedder): compare each document's fingerprint with the stored one, classify it as added, updated or unchanged, find documents that disappeared, embed all new chunks in one call, and write everything in a single transaction.

    $ python3 -m unittest -v tests.test_lab7_ship -k Store
    Hint

    dict(self.db.execute("SELECT doc_id, fingerprint FROM documents")) gives you the stored state in one line. with self.db: commits on success and rolls back on an exception.

  2. Watch it work

    $ python3 -m minirag index --db .minirag/index.sqlite
$ python3 -m minirag index --db .minirag/index.sqlite

    The first run adds 24 documents; the second finds all 24 unchanged. Now copy the data folder somewhere, edit one value in a document, delete another, and point MINIRAG_DATA at the copy:

    $ cp -r ../../tracks/rag/data /tmp/lumen-data
$ sed -i.bak 's/800 ms total deadline/750 ms total deadline/' /tmp/lumen-data/docs/catalog-api-timeouts.md
$ rm /tmp/lumen-data/docs/vendor-cdn-note.md /tmp/lumen-data/docs/*.bak
$ MINIRAG_DATA=/tmp/lumen-data python3 -m minirag index --db .minirag/index.sqlite
    .minirag/index.sqlite: 108 chunks
  added       0
  updated     1  catalog-api-timeouts
  unchanged  22  adaptive-bitrate-ladder catalog-api-timeouts-2023 cdn-operations …
  deleted     1  vendor-cdn-note
  embedded    0 chunk(s)

    Add --retriever hybrid and the vectors are stored too: every document is "updated" once (the embedder is part of the fingerprint), then only edited ones are re-embedded.

  3. The request handler

    RagService.handle_ask(payload, headers) returns (status, body). Validate in the order of the docstring, call ask(), map ModelError to 502 and any other exception to 500, and write exactly one trace per request. It's a plain function, so the tests call it directly; the web framework is only an adapter.

    $ python3 -m unittest -v tests.test_lab7_ship

  4. Serve it

    $ python3 -m minirag serve --db .minirag/index.sqlite --llm ollama:llama3.2:3b

    Without FastAPI installed it falls back to a standard-library server. With pip install fastapi uvicorn you also get interactive API docs at http://127.0.0.1:8000/docs. In another terminal:

    $ curl -s localhost:8000/ask -H 'X-User-Role: engineer' -H 'Content-Type: application/json' \
    -d '{"question": "What is the current production timeout for catalog API requests?"}'
$ curl -s localhost:8000/ask -d '{"question": "hi"}'
$ tail -2 .minirag/traces.jsonl
    {"error": "unknown or missing role", "request_id": "011088dff6db42e1"}

  5. Containerize

    Copy the Dockerfile's comment: build from the repository root so the course data is in the build context.

    $ cd ../..
$ docker build -f projects/knowledge-assistant/Dockerfile -t minirag .
$ docker run --rm -p 8000:8000 -e MINIRAG_LLM=ollama:llama3.2:3b -e OLLAMA_HOST=http://host.docker.internal:11434 minirag

    The image runs as a non-root user, has a health check, and takes its configuration from MINIRAG_* environment variables. On Linux, add --add-host=host.docker.internal:host-gateway to reach Ollama on the host.

Experiments

  • Break the modelStop Ollama (or set a wrong OLLAMA_HOST) while the server runs and send a question.
    Look for: a 502 with a request id, no hostnames in the body, and the error in the trace line. That's what lets on-call debug without exposing internals.
  • Measure latencySave this as loadtest.py and run it against your server with the extractive LLM and then a real one: 
    import json, statistics, time, urllib.request
from concurrent.futures import ThreadPoolExecutor

QUESTIONS = [q["question"] for q in json.load(open("../../tracks/rag/data/questions.json"))]

def ask(question):
    start = time.perf_counter()
    request = urllib.request.Request("http://127.0.0.1:8000/ask", data=json.dumps({"question": question}).encode(),
                                     headers={"X-User-Role": "engineer", "Content-Type": "application/json"})
    urllib.request.urlopen(request).read()
    return (time.perf_counter() - start) * 1000

with ThreadPoolExecutor(max_workers=4) as pool:
    ms = sorted(pool.map(ask, QUESTIONS * 3))
print(f"{len(ms)} requests · p50 {statistics.median(ms):.0f} ms · p95 {ms[int(len(ms) * 0.95)]:.0f} ms")
    Look for: the gap between p50 and p95, and how both change with concurrency (max_workers). Compare with the timings in your traces: which stage grows?
  • Cost your own setupPut your real numbers in the calculator above: your k, your average chunk tokens (the tokens column of eval divided by k), your provider's prices.
    Look for: the monthly cost at 10× your expected traffic, and which single setting would halve it.

Done when python3 -m unittest -v tests.test_lab7_ship passes and curl gets a cited answer from your running service.

GO FURTHER

Optional

  • pgvector. Run pgvector/pgvector in Docker, write an IndexStore with the same methods on Postgres, and do vector search in SQL (ORDER BY embedding <=> $1 LIMIT k). Add an HNSW index and compare with exact search.
  • Streaming. Add a /ask/stream endpoint that streams tokens as server-sent events, and measure time to first token instead of total time.
  • OpenTelemetry. Replace the JSON trace with spans per stage (retrieve, pack, generate) and look at them in Jaeger.
  • Deploy. Run the image on a managed container service (AWS App Runner or ECS, Google Cloud Run, Azure Container Apps) with a hosted model API, the index on a volume or in a managed Postgres, and the API key in the platform's secret store.
