MODULE 02 · RETRIEVE

Search by meaning, not spelling

Keyword search can't see that "undo a bad release" means "roll back". Embedding models can: they turn text into vectors whose direction captures meaning. You'll see what cosine similarity measures, then build vector search with a cache, and plug in a real embedding model.

Vectors, angles and nearest neighbours

An embedding is a point in meaning-space

An embedding model maps a piece of text to a list of numbers, a vector: 384 numbers for all-MiniLM-L6-v2, 768 for nomic-embed-text. It's trained on millions of pairs of related texts (a question and its answer, a title and its article) to put related texts close together and unrelated ones far apart. Nobody chooses what each dimension means; what matters is which vectors end up close.

"Close" means pointing in a similar direction. The usual measure is cosine similarity: the cosine of the angle between two vectors. It's 1 when they point the same way, 0 when they're unrelated (at 90°) and −1 when they're opposite. It ignores length, so a long passage and a short question can still match.

Normalize once, then use dot products. If every vector is scaled to length 1, the dot product is the cosine. Vector databases rely on this: normalize at indexing time, then searching is just multiply-and-add.

Nearest neighbours: what vector search returns

To search, embed the question with the same model and return the chunks whose vectors are most similar. The map below is a hand-drawn 2-D cartoon of what an embedding model does. Real models work in hundreds of dimensions, and you'll use one in the lab. Notice that the nearest sentences often share no words with the question.

Keyword and vector search fail differently

QueryKeyword (BM25)Vector
Exact identifiers: PLAY-4019, CATALOG_DEADLINE_MSStrong: rare token, high IDFOften weak: codes have little "meaning" to the model
Paraphrases: "undo a bad release"Weak: needs the same wordsStrong: that's what it's trained for
Numbers and negation: "not in staging", "under 2%"WeakWeak: "approval needed" and "no approval needed" look alike
Your company's jargonFine if the words matchDepends on whether the model saw similar text

Because they fail differently, production systems often run both and merge the results. That's Module 6.

Exact versus approximate search

Comparing the query with every vector (exact, or brute-force, search) is fine for thousands of chunks. At millions, vector databases (pgvector, OpenSearch, Qdrant, Pinecone…) use approximate nearest neighbour indexes such as HNSW, a graph you walk from neighbour to neighbour. It's much faster, but may miss some true neighbours, so measure ANN results against exact search on your own data before trusting them.

Practicalities that bite

  • Same model for questions and documents. Vectors from different models aren't comparable, even if they have the same length.
  • Prefixes. Some models expect a task prefix; nomic-embed-text wants search_query: and search_document: . The supplied adapter adds them.
  • Cache embeddings. Embedding is the slow, sometimes paid, step. Key the cache by model name and text, so changing either re-embeds.
  • Memory. 1 million chunks × 768 dimensions × 4 bytes ≈ 3 GB of floats, before any index overhead.

Key takeaways

  • Embeddings place text so that similar meaning means similar direction; cosine similarity measures that direction.
  • Vector search finds paraphrases that keyword search misses, and misses exact codes that keyword search finds.
  • Normalize, cache by model + text, and use the same model on both sides.

Lab 2: vector search with a cache

Goal: run dense retrieval over the knowledge base, first with the offline stand-in, then with a real embedding model, and compare it with your BM25.

You write: minirag/embeddings.py → cosine, normalize, CachedEmbedder.embed_documents · minirag/vectors.py → VectorIndex.search

  1. Similarity

    Implement cosine(a, b) and normalize(v) with the supplied dot and norm. Zero vectors must not crash.

    $ python3 -m unittest -v tests.test_lab2_vectors -k Similarity

  2. Exact vector search

    Implement VectorIndex.search: embed the query with embed_query, normalize it, take the dot product with every allowed item's vector (they're normalized when the index is built), sort by score then id, return the top k.

    $ python3 -m unittest -v tests.test_lab2_vectors -k VectorSearch

  3. Embedding cache

    Implement CachedEmbedder.embed_documents: work out which texts are missing from the cache, send only those to the real embedder in one call, store and save them, and return vectors in the original order.

    $ python3 -m unittest -v tests.test_lab2_vectors
    Hint

    Compute keys = [self.key("doc", t) for t in texts] first. De-duplicate the missing texts so a text repeated in one batch is embedded once.

  4. Run it offline

    The default embedder is HashingEmbedder: it hashes words and three-letter fragments into 512 numbers. It needs no download, and it matches spelling, not meaning.

    $ python3 -m minirag search "how do I undo a bad playback release" --retriever dense --chunks document --k 3
    dense · 24 chunks (document) · role=engineer

 1.   0.487  playback-rollback-runbook
 2.   0.439  playback-architecture
 3.   0.296  playback-error-codes

    It got this one right through the shared fragments "playback" and "release", not because it understood "undo". Try a question with no shared words, like "A customer's TV keeps refusing to play a film they paid for", and you'll see how little it knows.

  5. Plug in a real model

    Pick one: everything else stays the same.

    # local, via Ollama (setup page)
$ python3 -m minirag search "A customer's TV keeps refusing to play a film they paid for" --retriever dense --embedder ollama:nomic-embed-text
# local, via Hugging Face
$ pip install sentence-transformers
$ python3 -m minirag search "A customer's TV keeps refusing to play a film they paid for" --retriever dense --embedder st:sentence-transformers/all-MiniLM-L6-v2

    The first run embeds all 112 chunks and caches them in .minirag/cache/; later runs only embed the query.

Experiments

  • Paraphrases: keyword vs vectorRun these three with --retriever bm25 and with a real embedder: "How do I undo a bad playback release?", "Why did the home screen go blank after a catalog deploy in the summer?", "Who signs off on switching a feature off with a kill switch in the middle of an incident?" Note the rank of the right document (rollback runbook, catalog cache postmortem, incident commander guide).
    Look for: questions phrased in a user's words rather than the document's. You'll score this properly in Module 5 with the paraphrase question type.
  • Exact codesSearch PLAY-4019 and CATALOG_DEADLINE_MS with the real embedder.
    Look for: where the error-code table and the timeout standard land compared with BM25. This is the case for hybrid search.
  • What the cache saves youDelete .minirag/cache/ and time a search (time python3 -m minirag search ...), then time it again. Open the cache file: how many entries, and how large?
    Look for: indexing cost dominates the first run. In production that's a batch job, not something a user waits for (Module 7).
  • Two models, one questionCompare nomic-embed-text and all-MiniLM-L6-v2 on the same five questions.
    Look for: the model is a parameter you choose with an evaluation, not a constant. Public leaderboards such as MTEB are a starting point, not an answer for your documents.
