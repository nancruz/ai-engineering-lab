Search by meaning, not spelling

Keyword search can't see that "undo a bad release" means "roll back". Embedding models can: they turn text into vectors whose direction captures meaning. You'll see what cosine similarity measures, then build vector search with a cache, and plug in a real embedding model.

LEARN

From words to vectors, and how a vector database searches them

This page builds the idea up from nothing: what a vector is, how you'd turn a sentence into one, how two vectors are compared, and what a vector database actually does when you search it. Each step has something to play with. No maths beyond multiplying and adding.

The problem: same meaning, different words

In Module 1, the question "how do I undo a bad release?" didn't find the rollback runbook, because the runbook says "roll back" and BM25 only matches identical terms. A person sees immediately that these mean the same thing. To get a computer to see it, we need a way to represent what a text is about that doesn't depend on its exact words. That representation is a vector.

Step 1 · A vector is just a list of numbers

A vector is an ordered list of numbers, like [0.9, 0.2]. With two numbers you can draw it: go 0.9 to the right and 0.2 up, and draw an arrow from the origin to that point. With three numbers it's an arrow in 3-D space. With 768 numbers you can't draw it anymore, but all the arithmetic works exactly the same way, which is the only reason any of this is practical.

Each position in the list is a dimension. Two vectors can only be compared if they have the same number of dimensions and each position means the same thing in both.

Step 2 · A hand-made embedding

Suppose we describe every sentence with four scores between 0 and 1: how much it's about releases & rollback, video playback, billing & rights, and time & speed. "Roll back production when the canary error ratio stays above 2%" might be [0.9, 0.2, 0, 0.1]: very much about rollback, a little about playback, nothing about billing. "How do I undo a bad release?" might be [0.9, 0.3, 0, 0].

Look at what just happened: the two sentences share no words, but their numbers are almost the same. That list of numbers is an embedding: a text, placed as a point in a space where each direction stands for some aspect of meaning. Search then becomes "find the stored vectors whose numbers look most like the question's numbers".

Step 3 · Comparing two vectors: dot product, length, cosine

The widget used three small calculations. They are the core of every vector search, so here they are slowly.

Dot product

Multiply the two vectors position by position and add everything up. For [0.9, 0.3, 0, 0] and [0.9, 0.2, 0, 0.1]: 0.9×0.9 + 0.3×0.2 + 0×0 + 0×0.1 = 0.87. A position contributes only when both vectors are high there, so the dot product is large when they're strong on the same topics.

Length (norm)

The length of the arrow: square each number, add, take the square root. [0.9, 0.3, 0, 0] has length √(0.81 + 0.09) = 0.95. A vector with bigger numbers everywhere is longer, and it gets bigger dot products with everything, a bit like a long document in BM25.

Cosine similarity

The dot product divided by both lengths: 0.87 / (0.95 × 0.93) = 0.99. Dividing cancels out the lengths, leaving only the direction. It's the cosine of the angle between the two arrows: 1 = same direction, 0 = at right angles (unrelated), −1 = opposite.

Why direction, not length?

With embeddings, length mostly reflects things like how long or wordy the text is, not what it's about. A one-line question and a long paragraph about the same topic should match. Comparing directions makes that happen.

Drag the arrows to get a feel for it. Notice that making an arrow longer changes the dot product but not the cosine.

Normalize once, then use dot products. If you divide every vector by its own length beforehand, every vector has length 1, and the dot product is the cosine (the division by 1 × 1 does nothing). That's why vector databases normalize at indexing time: searching becomes pure multiply-and-add, which hardware is very good at. Step 4 · Real embedding models learn their own dimensions

Nobody hand-labels dimensions in practice. An embedding model is a neural network that reads a text and outputs a fixed-size vector: 384 numbers for all-MiniLM-L6-v2, 768 for nomic-embed-text, whether the input is three words or three paragraphs. A real output looks like [0.031, −0.112, 0.087, 0.004, …], and no single number means anything you could name.

How does it learn to put similar meanings close together? It's trained on millions of pairs of texts known to belong together: a question and its accepted answer, a title and its article, a search query and the page people clicked. Training repeatedly nudges the network so that each pair's vectors point in more similar directions and unrelated texts point in less similar ones. After enough of this, "undo a bad release" and "roll back production" end up close, because texts like them kept appearing together in the training data.

Two consequences matter for you as an engineer:

  • You can't inspect a dimension to debug a result. You can only look at which texts ended up close. Evaluation (Module 5) is how you find out whether the model's notion of "similar" matches yours.
  • The model only knows what its training data covered. Your company's internal jargon or error codes may land in odd places.

Step 6 · What a vector database actually is

Strip away the marketing and a vector database (pgvector, OpenSearch, Qdrant, Pinecone, Chroma…) does three jobs:

JobWhat it meansIn your lab
Store recordsEach record: an id, the vector, the original text, and metadata (document, section, access level, date…).A Python list of chunks with their normalized vectors
Find nearest neighboursGiven a query vector, return the k records with the highest similarity.VectorIndex.search: a loop computing every dot product (exact search)
FilterOnly consider records matching conditions: this user's access level, current documents, a product area.The allow(item) function, applied before scoring

For the 112 Lumen chunks, a plain loop is the right answer: exact, simple, instant. The database earns its keep at scale, and the hard part there is the second job.

Step 7 · Approximate search: how vector databases go fast

Exact search compares the question with every stored vector. At 10 million vectors × 768 numbers that's about 7.7 billion multiplications for each question. Too slow. So vector databases build an approximate nearest neighbour (ANN) index, which finds almost always the nearest vectors while looking at only a small fraction of them.

The most common one is HNSW (Hierarchical Navigable Small World). The core idea is easy to see in 2-D: at indexing time, link every vector to a few of its nearest neighbours, making a graph. To search, start at an entry point and keep hopping to whichever neighbour is closer to the question; stop when none is. Like finding a house by asking each neighbour "who lives closer to this address?".

What to take from it:

  • It's fast because each hop only computes distances to a handful of neighbours, so most vectors are never looked at.
  • It can miss. The walk can get stuck at a point that's closer than all its neighbours but isn't the true nearest. Set the links to 1 or 2 and click around to find such places.
  • The knobs trade speed for accuracy. More links per point (called M in HNSW) and a wider search (ef_search, roughly "how many candidates to keep exploring") miss less but compute more distances. More links also means more memory.
  • The "hierarchical" part adds a few sparser layers on top, with long links, so the walk first crosses the space in big jumps and then refines in the dense bottom layer. Same greedy idea, fewer hops.

The quality measure for an ANN index is recall against exact search: of the true top 10, how many did the index return? Production setups typically tune for 95–99%. Always check this on your own data before trusting the defaults.

Filters and ANN don't mix easily. If you search the graph first and filter afterwards ("post-filtering"), a restrictive filter (say, only SRE-visible chunks) can leave you with fewer than k results. Filtering first ("pre-filtering") is correct but breaks the graph's shortcuts. Databases handle this in different ways; it's worth knowing which yours uses. Your exact search doesn't have this problem: it filters, then scores everything that's left.

Keyword and vector search fail differently

QueryKeyword (BM25)Vector
Exact identifiers: PLAY-4019, CATALOG_DEADLINE_MSStrong: rare token, high IDFOften weak: codes have little "meaning" to the model
Paraphrases: "undo a bad release"Weak: needs the same wordsStrong: that's what it's trained for
Numbers and negation: "not in staging", "under 2%"WeakWeak: "approval needed" and "no approval needed" look alike
Your company's jargonFine if the words matchDepends on whether the model saw similar text

Because they fail differently, production systems often run both and merge the results. That's Module 6.

Practicalities that bite

  • Same model for questions and documents. Vectors from different models aren't comparable, even if they have the same length. Changing models means re-embedding everything.
  • Prefixes. Some models expect a task prefix; nomic-embed-text wants search_query: and search_document: . The supplied adapter adds them.
  • Cache embeddings. Embedding is the slow, sometimes paid, step. Key the cache by model name and text, so changing either re-embeds.
  • Memory. 1 million chunks × 768 dimensions × 4 bytes ≈ 3 GB of floats, before any index overhead.
  • Scores are relative. A cosine of 0.6 can be a great match with one model and a poor one with another. Don't hard-code a threshold without measuring.

Key takeaways

  • An embedding is a list of numbers placing a text in a space where similar meaning means similar direction. Models learn this from millions of related text pairs.
  • Cosine similarity = dot product ÷ both lengths = how aligned two vectors are. Normalize once and the dot product is enough.
  • A vector database stores vectors with their text and metadata, finds nearest neighbours, and filters. At scale it uses an approximate index like HNSW, trading a little recall for a lot of speed.
  • Vector search finds paraphrases that keyword search misses, and misses exact codes that keyword search finds.

Lab 2: vector search with a cache

Goal: run dense retrieval over the knowledge base, first with the offline stand-in, then with a real embedding model, and compare it with your BM25.

You write: minirag/embeddings.py → cosine, normalize, CachedEmbedder.embed_documents · minirag/vectors.py → VectorIndex.search

  1. Similarity

    Implement cosine(a, b) and normalize(v) with the supplied dot and norm. Zero vectors must not crash.

    $ python3 -m unittest -v tests.test_lab2_vectors -k Similarity

  2. Exact vector search

    Implement VectorIndex.search: embed the query with embed_query, normalize it, take the dot product with every allowed item's vector (they're normalized when the index is built), sort by score then id, return the top k.

    $ python3 -m unittest -v tests.test_lab2_vectors -k VectorSearch

  3. Embedding cache

    Implement CachedEmbedder.embed_documents: work out which texts are missing from the cache, send only those to the real embedder in one call, store and save them, and return vectors in the original order.

    $ python3 -m unittest -v tests.test_lab2_vectors
    Hint

    Compute keys = [self.key("doc", t) for t in texts] first. De-duplicate the missing texts so a text repeated in one batch is embedded once.

  4. Run it offline

    The default embedder is HashingEmbedder: it hashes words and three-letter fragments into 512 numbers. It needs no download, and it matches spelling, not meaning.

    $ python3 -m minirag search "how do I undo a bad playback release" --retriever dense --chunks document --k 3
    dense · 24 chunks (document) · role=engineer

 1.   0.487  playback-rollback-runbook
 2.   0.439  playback-architecture
 3.   0.296  playback-error-codes

    It got this one right through the shared fragments "playback" and "release", not because it understood "undo". Try a question with no shared words, like "A customer's TV keeps refusing to play a film they paid for", and you'll see how little it knows.

  5. Plug in a real model

    Pick one: everything else stays the same.

    # local, via Ollama (setup page)
$ python3 -m minirag search "A customer's TV keeps refusing to play a film they paid for" --retriever dense --embedder ollama:nomic-embed-text
# local, via Hugging Face
$ pip install sentence-transformers
$ python3 -m minirag search "A customer's TV keeps refusing to play a film they paid for" --retriever dense --embedder st:sentence-transformers/all-MiniLM-L6-v2

    The first run embeds all 112 chunks and caches them in .minirag/cache/; later runs only embed the query.
