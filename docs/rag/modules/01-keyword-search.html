How keyword search ranks documents

Retrieval decides what the model can know

A language model in a RAG system only answers from the passages you put in front of it. Retrieval picks those few passages out of everything you have. If the passage with the answer isn't retrieved, nothing later in the pipeline can recover it. That's why the course starts here, and why most RAG debugging starts by asking "was the right passage retrieved?"

The inverted index

Scanning every document for every query is too slow. A search engine builds an inverted index once: like the index at the back of a book, it maps each term to the documents that contain it. A query looks up its terms and only scores the documents on those lists.

The "terms" come from a tokenizer: lowercase the text, split it into words, drop words like "the" and "how" that appear everywhere. Small choices here matter. Should PLAY-4012 be one term or two? You'll decide in the lab.

Scoring with BM25: three ideas

Once you have candidates, you need an order. BM25 adds up a score for every query term a document contains, built from three intuitions:

1. Rare terms matter more

"playback" is in many Lumen documents, so it says little. "PLAY-4012" is in two. IDF (inverse document frequency) gives each term a weight that grows as fewer documents contain it.

2. Repeats help, with diminishing returns

A document mentioning "timeout" five times is probably more about timeouts than one mentioning it once, but not five times more. k1 controls how fast extra occurrences stop counting.

3. Long documents shouldn't win by being long

A long handbook contains more words, so it matches more queries by chance. b controls how much a document's length (compared with the average) dampens its score.

Put together

score = Σ over query terms of idf(term) × saturated, length-normalized term frequency. No training, no model: just counting, and it's still hard to beat on exact terms.

The formula
score(d, q) = Σt ∈ q idf(t) · tf(t,d) · (k1 + 1) / ( tf(t,d) + k1 · (1 − b + b · |d| / avgdl) )
idf(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) )

tf(t,d): occurrences of t in d · df(t): documents containing t · N: number of documents · |d|: terms in d · avgdl: average |d|. Common defaults: k1 between 1.2 and 2.0, b = 0.75. This is the "+1 inside the log" variant used by Lucene, which keeps IDF positive.

Things to try in the explorer:

  • k1 = 0 makes every term count once, however often it appears. Watch the saturation curve flatten.
  • catalog timeout retries: the archived 2023 standard (3000 ms, three retries) ranks above the current one. BM25 measures word overlap, not truth or freshness. You'll fix that with metadata in Module 4.
  • how do I undo a bad playback release: the deploy pipeline page wins on "bad" and "release". The runbook says "roll back", which isn't the same word. That's the vocabulary mismatch Module 2 addresses.

Key takeaways

  • Retrieval quality caps answer quality: a passage that isn't retrieved can't be used.
  • An inverted index makes keyword search fast; BM25 ranks with rarity (IDF), saturation (k1) and length normalization (b).
  • Keyword search is excellent at exact identifiers and blind to synonyms, freshness and permissions.

Lab 1: a tokenizer and a BM25 index

Goal: search the Lumen knowledge base from your terminal with your own BM25, and explain every score.

You write: minirag/text.py → tokenize() · minirag/lexical.py → BM25Index.__init__, idf, term_scores, search

  1. Tokenize

    Implement tokenize(text): lowercase, find terms with the supplied TOKEN regex, keep compounds like play-4012 whole and add their parts (play, 4012), drop stopwords. The docstring has an example.

    $ python3 -m unittest -v tests.test_lab1_search -k Tokenize
    Hint

    re.split(r"[-_]", match) gives the parts. Build a list in order; the tests check the order.

  2. Build the inverted index

    In BM25Index.__init__, for each item tokenize item.search_text() and record: a Counter of term frequencies, the document length, the document frequency of each term (once per item), and the postings (term → list of item positions).

    $ python3 -m unittest -v tests.test_lab1_search -k BuildIndex

  3. Score

    Implement idf(term) and term_scores(query_terms, position) from the formula above. A query term that appears twice counts once. Terms absent from the item are left out of the result.

    $ python3 -m unittest -v tests.test_lab1_search -k Scoring
    Hint

    dict.fromkeys(query_terms) de-duplicates while keeping order. Compute the length-normalization factor once per item, outside the loop.

  4. Search

    Implement search(query, k, allow): collect candidate positions from the postings of the query terms, skip items where allow(item) is false, sum each candidate's term scores, sort by score (highest first) then by id, and return the top k (item, score) pairs.

    $ python3 -m unittest -v tests.test_lab1_search

  5. Run it

    Search whole documents (Module 3 introduces smaller chunks) and ask for the per-term breakdown:

    $ python3 -m minirag search "PLAY-4012" --chunks document --k 3 --explain

    Look for: the scores of play vs play-4012 in --explain. The parts make partial matches possible; the whole compound keeps its high IDF.

Then search "kill switch flag" and look at the feature-flags policy: it says "Kill switches" and "flags". Add a small plural rule to tokenize (strip es after ch/sh/x, otherwise a trailing s, for words longer than 3 letters) and search again.
    Look for: stemming fixes plurals (flags → flag), not synonyms (undo vs roll back). Synonyms need meaning, which is Module 2. Keep the stemmer only if Module 5's numbers say it helps.
