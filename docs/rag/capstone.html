CAPSTONE · 6–10 HOURS

Make it work on documents you care about

The Lumen knowledge base was designed to teach. Real documentation is messier: longer pages, inconsistent structure, questions nobody anticipated. In the capstone you point your system at a real document set, write the evaluation set yourself, and improve the system one measured change at a time. The result is a project you can show and explain in an interview.

no new code requiredyour choices, your numbers

1. Pick a document set

Choose 30–200 Markdown pages you understand well enough to judge answers. Good options:

  • Your team's documentation: runbooks, ADRs, onboarding notes. Check that you're allowed to copy it, keep it out of public repositories, and remove credentials and personal data first. The data retention policy in the Lumen docs is a reasonable checklist.
  • Open-source documentation in Markdown: for example the docs folders of FastAPI, Kubernetes or PostgreSQL's wiki exports. Note the license in your README.

Put the files in one folder. Front matter is optional: without it, the id is the file name, the status is current and access is all. Add status: archived or access: sre where it matters.

$ python3 -m minirag search "your first question" --docs ~/capstone/docs
$ python3 -m minirag chunks some-page --docs ~/capstone/docs

2. Write 25 questions before tuning anything

This is the most valuable part of the capstone, and of real RAG work. Write questions the way real users would ask them, and label them from the documents, not from what your system returns. Aim for a spread of types:

TypeHow manyExample shape
exact5names a config key, command, error or version
paraphrase6describes the problem in a user's words, not the doc's
multi-doc4needs two pages to answer completely
procedure4"how do I…": the answer is a sequence of steps
missing4sounds answerable but the docs don't say: the system must abstain
your call2+freshness, access, conversational follow-ups…

Same format as the course questions. Only id and question are required; the rest makes the metrics work:

[
  {"id": "c01", "question": "How do I rotate the database password without downtime?",
   "relevant": ["db-credentials"], "evidence": ["both passwords are valid for one hour"],
   "must_include": ["one hour"], "type": "procedure", "split": "dev"},
  {"id": "c02", "question": "Who owns the billing service?", "relevant": [], "type": "missing", "split": "dev"}
]

Keep 5 of them with "split": "test" and don't look at their results until the end.

3. Baseline, then three measured improvements

$ python3 -m minirag eval --docs ~/capstone/docs --questions ~/capstone/questions.json \
    --compare bm25,hybrid --answers --llm ollama:llama3.2:3b --show-failures --out runs/baseline.json

Read every failure. Group them by cause: wrong chunk boundaries? vocabulary mismatch? the answer spans two pages? the model ignored the sources? Then pick the three changes you expect to help most (chunk size or strategy, embedder, hybrid, reranker, multi-query, k, prompt wording, a better model) and for each one:

  1. change one thing;
  2. rerun the same command with a new --out file;
  3. keep it only if the numbers improve on the question types it was meant to fix, without breaking others.

Finish with one run on the test split.

4. Ship it and write it up

Serve the final configuration with Docker (Module 7) and write a README with:

  • the problem and the documents (and their license or permission);
  • an architecture diagram of your final pipeline;
  • a results table: baseline and each change, on dev and finally on test, with tokens and latency;
  • three failures you couldn't fix and why;
  • what you'd do next with more time or budget.

That README is the interview answer. "I built RAG" is common. Something like "hybrid search raised evidence recall on paraphrase questions from 0.6 to 0.85 for 40 ms more latency; the reranker didn't pay for itself, so I removed it" is not.

Done when you have a question set, a baseline, three measured changes, a test-split result and a README that explains the decisions.

Where to go next

  • The agents course: give the model tools (including your retriever) and let it decide what to call. Everything from Module 4 about untrusted text and least privilege gets more important.
  • Structured data: add a tool that answers from SQL tables when the question is about numbers, and route between it and retrieval.
  • Fine-tune an embedding model on question/passage pairs from your evaluation set and measure it against the off-the-shelf model.
